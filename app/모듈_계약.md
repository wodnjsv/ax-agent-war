# 모듈 계약 (W01 공통 뼈대 v1)

이름(객체·필드·열거값·사건)의 기준은 `problem4/공통_접점.md`다. 이 문서는 코드를 붙이는 방법만 정한다.
외부 의존성 0개: Node 22(≥22.13), ES 모듈, `node:http`, `node:sqlite`, `node:test`, 내장 `fetch`만 쓴다.

## 2. 등록

```js
export async function register(ctx) { /* 테이블 정의, 구독, 경로, expose */ }
```
- 모듈은 p1→p4 순서로 한 번 등록된다. 등록 중 오류가 나면 그 모듈만 빠지고 앱은 뜬다(`/api/meta`의 `modules[].error`).
- 등록 단계에서는 다른 모듈을 부르지 않는다(아직 없을 수 있다). 호출은 사건 처리·경로 처리·onInit 안에서 한다.

| `ctx.defineTable(name, columnsDdl)` | 이름은 `pN_`로 시작해야 한다(예: `p2_supply_judgment`). `CREATE TABLE IF NOT EXISTS`로 만들고 초기화 대상에 등록 |
| `ctx.events.emit(e)` | 사건 저장·전파. 5절 |
| `ctx.events.on(types, fn)` | `types`: 사건 이름, 배열, `'*'`. `fn(event)`는 async 가능 |
| `ctx.events.query(filter)` / `get(id)` | `filter`: `plan_id`, `event_type`(문자열·배열), `subject_id`, `scenario_id`, `emitted_by`, `since`, `limit`, `order('asc'|'desc')` |

| `ctx.httpError(status, msg)` | `throw ctx.httpError(404, '…')` |
| `ctx.expose(api)` / `ctx.module('p1')` | 4절 |
| `ctx.onInit(fn)` | 새 DB와 초기화 직후 p1→p4 순으로 실행(초기 자료 적재, 초기 사건) |
| `ctx.onReset(fn)` | 초기화 직전 행 삭제 뒤 실행(메모리 캐시 비우기) |
| `ctx.addPlanSummary(fn)` | 기안 목록·상세의 상태 요약. `fn(planId)` → `{ label, value, source_type, is_synthetic, is_simulation, step? }` 또는 배열. 목록 열은 (문제, `label`)로 고른다: 문제 1 `수요 입력`, 문제 2 `공급 판정`, 문제 3 `승인권자`·`승인 상태`, 문제 4 `확정`·`다음 마감(…)`. `step`(`p1`~`p4`)이 있으면 열이 아니라 기안 상세 진행 요약의 그 단계 마감으로 쓴다 |
| `ctx.log(...)` | `[pN]` 접두어 로그 |

## 4. 모듈끼리 부르기

- 소유자는 계산 결과를 함수로 내놓는다: `ctx.expose({ baselineDemand(skuId) {…}, … })`.
- 쓰는 쪽은 호출 시점에 `ctx.module('p1')?.baselineDemand('SKU-3001')`. 없으면 `null`이므로 "연결 안 됨"으로 처리한다.
- 다른 모듈의 테이블을 직접 SELECT하지 않는다. 다시 계산하지 않는다(공통_접점 0절, C1).
- 변화의 전달은 사건으로 한다(예: 문제 1 `DEMAND_INPUT_REVISED` → 문제 4 재검토 → 문제 2 재판정). expose는 현재 값을 읽을 때 쓴다.
- expose 함수 이름과 반환 형식은 소유 문제가 자기 명세에 적고, 반환 객체의 필드 이름은 사전 3절을 따른다.

## 5. 사건

```js
await ctx.events.emit({
  event_type: 'SUPPLY_JUDGED',        // 필수. 사전 5절 등록표 밖이면 거부
  source_type: '계산',                // 필수. 원본도출|계산|사람입력|모의회신|가정
  plan_id: 'PLAN-002',                // 기본 'NONE'
  subject_type: 'supply_judgment', subject_id: 'SJ-…',
  actor_dept: 'SCM', actor_role: '…', // 기본 'SYSTEM'. MKT|SCM|FIN|MS_MGMT|GROUP|COREVIA|SYSTEM
  occurred_at, effective_at,          // 기본: 가상 일자. occurred_at '미상'이면 effective_at 필수
  is_synthetic,                       // 기본 false
  is_simulation,                      // 기본: is_synthetic 또는 source_type이 사람입력·모의회신·가정이면 true
  premise_refs, caused_by, scenario_id /*기본 'BASE'*/, source_ref, generation_reason, spec_ref,
  payload: { … },                     // 사전 5절의 payload 필드
});
```
- `event_id`(`EV-nnnnnn`), `seq`(같은 일자 순서), `recorded_at`(실제 시각), `emitted_by`(모듈 id)는 뼈대가 붙인다. 사건 행은 고치거나 지우지 않는다.
- **`is_simulation`은 전제를 모르는 뼈대가 사건 자체만 보고 정한다.** 가상 전제(수요 입력, 합성 속성 등)에 기댄 계산이면 내는 모듈이 `is_simulation: true`를 직접 넣는다(사전 2.1).
- 구독자는 저장 직후 등록 순서대로 불린다. 구독자 안에서 낸 사건은 큐에 쌓여 순서대로 처리되며, 바깥 `emit`은 큐가 빌 때 끝난다. 구독자 오류는 로그만 남기고 다음 구독자로 넘어간다.

## 6. AI (사전 8절)

```js
const r = await ctx.ai.call({ ai_task_type: 'structure', ai_task_name: 'demand_reply_structure',
  messages: [{ role: 'system', content: '…' }, { role: 'user', content: '…' }], input_refs: ['EV-…'], plan_id });
if (r.status === '미연결') { /* 담당자 직접 입력 화면으로 */ }
await ctx.ai.review({ ai_call_id: r.ai_call_id, review_result: '확인', reviewer_role: 'MKT-LINE-OWNER', plan_id });
```
- 모델은 `structure` → `anthropic/claude-opus-5.5`(`AI_MODEL_STRUCTURE`), `write` → `anthropic/claude-fable-5.2`(`AI_MODEL_WRITE`). `openrouter/auto`는 거부된다.
- 호출 성공 시 뼈대가 `AI_CALL_RECORDED`를 남긴다. 확인 결과는 `review()`가 `AI_OUTPUT_REVIEWED`로 남긴다. HTTP 실패는 예외로 던지고 기록하지 않는다. 호출한 쪽이 사람 입력으로 넘긴다.
- `structure`는 JSON만 받는다(`response_format: json_object`). 회신에 없는 값은 `null`, 사유는 `unclear_reasons` 배열로 받도록 프롬프트에 쓴다. 확인 전 결과는 판정에 쓰지 않는다.

## 7. 패널 규약 (`problemN/src/panel.js`, `/panels/pN.js`로 제공)

```js
export default {
  async renderPlan(el, { plan, api, ui }) { el.innerHTML = ui.table([...], rows); },  // 기안 상세의 자기 칸
  async renderMock(el, { api, ui }) { /* 모의 입력·날짜 진행 화면의 자기 칸(선택) */ },
};
```
- `api.get(path)`, `api.post(path, body)`: 자기 `/api/pN/...`를 부른다. `plan`은 원본 기안 객체다.
- `ui.esc`, `ui.table(cols, rows)`, `ui.krw`, `ui.num`, `ui.eok`(억 단위), `ui.tag(source_type, is_synthetic, is_simulation)`, `ui.label(code)`(코드 → 한국어 이름), `ui.section(title, body, { tag, note })`(전체 폭 구역), `ui.fold(title, body, { open, count })`(접는 목록). `ui.table`의 열에는 `tag`(열 제목의 자료 구분)와 `nowrap`을 줄 수 있다. `import { ui } from '/common.js'`로 직접 가져와도 된다.
- 화면 지침(조정자 (E)): 화면 문구는 한국어로 쓰고, 코드(GRP_CEO, on_schedule 등)는 `ui.label`로 한국어 이름을 보인다. 자료 구분(원본/계산/가정/모의/사람입력, 시뮬레이션)은 표 칸마다 반복하지 말고 구역 제목이나 열 제목에 한 번만 붙인다(`ui.tag`는 줄바꿈되지 않는 한 덩어리). 결론을 먼저 보이고, 긴 목록(재검토, 판정 버전, 주차별 표)은 `ui.fold`로 접고 결론이 바뀐 것만 먼저 보인다.
- 셸 배치: 기안 상세는 맨 위 진행 요약(수요 입력 → 공급 판정 → 승인 경로 → 확정, 단계별 상태와 마감) 아래 문제별 탭이다. 패널의 `renderPlan`은 탭 하나의 전체 폭을 쓴다. 모의 입력 화면은 시계 조작 → 문제 4 칸(시나리오·사건 순서표) → 문제 1~3 탭 순이다.
- 패널은 서버 계산을 보여주고 입력만 받는다. 판정·계산을 브라우저에서 하지 않는다.

## 11. 첫 화면과 설명 카드 (사용자 결정 2026-11-15)

주 사용자는 마케팅의 캠페인 기안 담당자다. 그 사람의 결정은 '이 기안을 확정기한 전에 확정해도 되는가, 바꿔야 하는가, 접어야 하는가'이고, 직접 하는 행동은 수요 입력·정정, 승인 요청 올리기, 대안 선택, 확정, 철회다. SCM·재무·승인권자·Corevia는 모의 입력으로 둔다.

### 11.1 화면 구조 (`#/`, `#/w/:plan_id[/demand|alternatives|approval]`)

- 왼쪽(업무 화면, `app/public/work.js`): 홈 '내 기안'(맨 위 기한 경고, 지금 내가 할 일 · 다른 부서를 기다리는 중 · 끝난 기안) / 기안 한 건(상태 한 문장 → 진행 단계 → 큰 행동 버튼 → 짧은 근거, 표·숫자는 접음) / 수요 입력(자유 서술 → AI 정리 → 확인·수정 → 등록, 직접 입력, 받을 수 있는 여지·품절 예상 참고) / 대안 비교 카드 / 승인 요청(승인권자·이유·AI 초안 수정 후 올리기) / 확정·철회 확인 창(브라우저 대화상자가 아닌 화면 안 창). 코드·영문 식별자·자료 구분 표시는 내지 않는다(표본 스케일·시뮬레이션 수량 주의만).
- 오른쪽(평가자 화면): 고정 흐름도(수요 입력 → 공급 판정 → 승인 경로 → 마감·재검토·확정, 원본·합성·계산 자료. 방금 사슬에 든 칸이 켜진다) / '방금 일어난 일'(행동 하나를 시작점으로 caused_by로 이어진 사건 카드. 주체 구분·사용한 데이터와 출처·규칙·결과, 자료 구분 표시는 여기서) / 시연 조작(1영업일, 다음 일정까지, 시나리오, 초기화, 직접 처리 켜기·끄기. 오른쪽 아래 고정) / 상세 근거 링크.
- 기존 화면은 '상세 근거'로 남는다: 기안 목록 `#/plans`, 문제별 탭 `#/plan/:id`, 사건 기록 `#/events`, 모의 입력 `#/mock`.

### 11.2 설명 카드 `describeEvent(event)` (각 모듈 공개 함수)

자기가 낸 사건을 받아 아래를 돌려준다. 모르는 사건이면 `null`.

```
{ title,            // 한 줄 제목. 예: '공급 판정: 조건부(보충 발주 필요)'
  actor_kind,       // '사람' | 'AI' | '규칙·계산' | '모의 입력'
  actor_label,      // 예: '마케팅 기안 담당자', 'SCM', '그룹 CEO', '시스템'
  inputs: [{ label, value, source, ref }],  // source: '원본' | '합성' | '계산' | '사람입력' | '모의회신' | '가정'. ref: 원본 파일·키 또는 사건 id
  rule,             // 적용한 규칙 한두 문장
  result,           // 결과와 상태 변화 한두 문장
  next }            // 이어지는 처리(선택)
```

- 평가자가 카드만 읽고 '어떤 데이터로, 어떤 규칙으로, 무엇이 바뀌었는지' 알 수 있게 한국어 업무 용어와 실제 수치로 쓴다. 계산하지 않고 저장된 값과 payload만 읽는다.
- 화면에서 사람이 한 행동은 `actor_kind='사람'`, 사건 순서표·기본 모의 입력은 `'모의 입력'`이다. 오른쪽 흐름은 위로 거슬러 오르다 '사람' 사건을 만나면 거기를 시작점으로 끊는다.
- 문제 4 `GET /api/p4/describe/:event_id`는 네 모듈 모두에 묻고 사건을 낸 모듈의 카드를 앞에, 다른 모듈의 카드를 `also[]`로 붙인다(예: `APPROVAL_REPLIED`는 문제 4 회신 카드 + 문제 3 반영 카드). 카드가 없으면 사건 이름과 payload 요약으로 대신하고 `fallback: true`를 붙인다. `AI_CALL_RECORDED`·`AI_OUTPUT_REVIEWED`는 공통 형식으로 대신한다.

### 11.3 화면용 API (문제 4)

| 경로 | 내용 |
|---|---|
| `GET /api/p4/user/home` | `{ sim_clock, alerts[], todo[], waiting[], done[], direct_plans[] }`. 항목: `plan_id`, `campaign_name`, `action`(`demand`/`alternatives`/`approval`/`confirm`), `label`, `due`, `days_left`(영업일), `overdue`, `waiting_on`, `sentence`, `auto`(자동 처리) |
| `GET /api/p4/user/plans/:plan_id` | 기안 한 건 묶음: `sentence`, `steps[4]`, `actions[]`(`kind`, `enabled`, `primary`, `blocked_reason`), `why`(공급·승인·마감 문장), `entry`(문제 1 `entryView`), `decision`(문제 2 `planDecision`), `approval`(문제 3 `approvalView`), `lapse_story` |
| `GET /api/p4/flow?plan_id=&limit=` | 행동 단위 사건 사슬 `{ groups[]{ root_event_id, trigger, cards[], modules[], sources[], total }, latest_user_action }`. 기안을 고르면 그 기안이 든 사슬만(묶음 상신처럼 기안 칸이 공통이어도 내용에 든 사건 포함) |
| `GET /api/p4/describe/:event_id` | 설명 카드(11.2) |
| `GET /api/p4/direct`, `POST /api/p4/plans/:plan_id/direct {on}`, `POST /api/p4/direct/all-auto` | 직접 처리 기안 목록(`pending[]`: 지금 사용자의 행동을 기다리는 직접 처리 기안)과 켜기·끄기, 모두 자동 처리로 |

- 직접 처리: 기안마다 켜면 마케팅 기안 담당자의 모의 입력(정시·늦은·정정 수요 회신, 대안 선택, 조기 공급 요청, 권장 대안, 기본 규칙의 시기 이동·철회, 확정, 기안 상신)을 건너뛰고 사용자가 왼쪽에서 한다. 다른 부서 회신(승인 회신, 조건 수용, 입고·재무·Corevia·그룹)은 계속 모의로 온다. 아무것도 하지 않으면 마감 경고·기한 경과가 규칙대로 난다(경위에 '담당자 입력 없음'). 기본값 PLAN-001~003. 시나리오처럼 초기화해도 유지된다.
- 직접 처리 공개 함수(문제 4): `listDirectPlans()` → 지금 직접 처리 기안 `plan_id[]`(부를 때마다 현재 값, 복사본), `isDirectPlan(plan_id)` → boolean. 모의 입력을 스스로 넣는 모듈(예: 문제 3 자동 묶음 상신)은 이 기안을 빼야 한다. 사용자가 고르는 화면(묶음 후보 등)에는 남겨도 된다.
- 수요 입력·대안 선택·승인 요청은 각 소유 문제의 경로를 그대로 부른다: 문제 1 `POST /api/p1/entry/:plan_id/{text,confirm,direct}`, `POST /api/p1/preview` / 문제 2 `POST /api/p2/alternatives/:id/select`(화면에서는 `is_mock: false`) / 문제 3 `POST /api/p3/draft`, `POST /api/p3/draft/:id/review`, `POST /api/p3/plan/:plan_id/approval/submit`. 확정·철회는 문제 4 `POST /api/p4/plans/:plan_id/{confirm,withdraw}`.
