# 합성 자료 작성 기준

이 프로젝트에서 합성 자료를 추가할 때 따르는 기준이다. 대회 공통 요건과 W01에서 정한 프로젝트 원칙을 구분한다. 합성 데이터의 양보다 정보 공백의 정의, 보완 이유, 실제 판단·처리에서의 사용과 검증이 중요하다.

- 정리일: 2026-11-14 (3절 범위 변경: 2026-11-15)
- 대회 문서 기준: v1.5, 2026-10-29
- 가상기업 기준일: 2026-07-01. 자료 작성일·대회 일정과 구분한다.
- 적용 대상: 합성 데이터, 모의 외부 회신, 추가 가정, 모의 매핑 및 이를 사용한 계산·실행 결과

## 1. 대회 공통 필수 요건

합성은 선택 사항이다. 필요한 정보를 원본에서 도출하거나, 담당자 확인·명시적 가정·합성으로 보완할 수 있다. 정보가 없다는 이유로 임의의 값을 넣기 전에 어떤 판단에 필요한 정보인지부터 정의한다.

| 구분 | 기록하거나 표시할 내용 | 근거 |
|---|---|---|
| 추가 행의 필수 항목 | 식별자, 적용 시점, 원본 연결, 생성 이유 | A05 §6 |
| 자료의 성격 | 원본 사실, 부서 주장·분석, 추가 가정, 합성 관측값, 계산 결과를 구분 | A05 §6, A03 §5 |
| 보완 이유 | 정보 공백과 영향받는 판단, 보완 방법을 선택한 이유 | A03 §5, A04 §2 |
| 범위와 의미 | 대상, 단위, 기간, 연결 기준. 모의 매핑이면 가정과 적용 범위 | A03 §5, A04 §2 |
| 실제 사용 위치 | 어떤 조회·계산·판단·승인·후속 처리에 쓰이는지 | A05 §6, A04 §2 |
| 가정과 제약 | 값·관계를 정한 전제, 비용·시간·수량·품질 등의 제약 | A03 §5, A05 §6 |
| 검증 | 주요 조건 변경 시 판단과 후속 처리의 타당성, 확인된 한계 | A03 §5, A04 §3, A05 §6 |
| 가상 입력 표시 | 모의 회신·검사 결과가 가상 입력임을 표시. 합성 결과를 실제 확보한 증거나 실제 성과로 제시하지 않음 | A05 §6 |
| 구현 범위 | 실제 작동, 모의 처리, 설계 단계를 구간별로 구분 | A04 작성 안내, A05 §6 |
| 버전과 재현 | 사용 자료·가정·업무 설계 버전, 데이터 위치·로드 방법, 대표 입력·실행 순서·결과 확인 위치 | A05 §6, A04 §5 |

추가 행의 필수 항목과 자료 단위의 설명은 연결해서 관리해도 된다. 모든 설명을 각 행에 반복할 필요는 없지만, 행에서 해당 설명과 원본을 추적할 수 있어야 한다. 아래의 파일 구성·필드명은 이 요건을 충족하기 위한 권장 방식이며 대회 지정 서식은 아니다.

## 2. 원본 보존과 시나리오 분리

- 원본 폴더는 그대로 보존한다. 정제·매핑·수식·확장 데이터는 별도 폴더에 두고 원본 행 또는 파일까지 추적할 수 있게 한다.
- 원본 정보가 없는 경우와 원본 기록이 충돌하는 경우를 구분한다. 불일치가 있다면 적용 범위와 처리 방식을 설명한다.
- 독점 공급·생산능력·계약·승인 제약을 변경하는 가정은 기본 사실에 덮어쓰지 않는다. 기준 상황과 대안 시나리오를 분리하고 변경 근거, 필요한 승인·전환 절차를 설명한다.
- 제약을 단순 삭제해 실행 가능하다고 주장하지 않는다. 공급자 회신·검사 결과를 항상 유리하게 만드는 것으로 검증을 대신하지 않는다.
- 마케팅 표본과 회사 전체 규모 자료를 수량·금액으로 연결하려면 대응표·규모·기간 가정을 별도로 정의하고 시뮬레이션 결과로 표시한다. 확대 근거가 없으면 금액 효과는 판단 유보한다.
- SKU·제품군·배치·로트·공장·라인을 이름이나 코드의 유사성만으로 일대일 연결하지 않는다. 확인된 키 연결과 모의 매핑을 구분한다.
- 예측·확정 주문·계획·실적·회수의 상태와 기간을 구분한다.

공통 형식은 UTF-8, 첫 행 헤더, 파이프(`|`) 구분 CSV다. 금액은 KRW·VAT 제외, 제품 수량은 EA, 원료는 kg이며 `NONE`은 0과 다르다. 사건 발생일과 적용일은 별도로 기록한다. 기본 업무 달력은 월~금 영업일·공휴일 없음이며, 추가 휴일은 별도 시나리오로 표시한다.

## 3. W01 프로젝트 원칙

다음은 현재 W01 해결 방식에서 정한 범위다. 대회 전체가 합성을 이 범위로 제한한 것은 아니다. 범위를 변경할 경우 변경 이유와 가정·설계 버전을 남긴다.

- 합성은 시스템이 받아야 할 외부 입력을 모의하는 데 사용한다. 판단에 필요한데 원본에 없는 속성을 마스터 자료(SKU·공급처·승인권자·기안)에 추가하는 데에도 사용한다. 과거 요청·승인 지연 이력은 만들지 않는다.
- 근거를 제시할 수 없는 전사 환산 계수, 품절 비용, 과거 지연 수치는 만들지 않는다. 표본 주문의 수량과 과거 캠페인의 판매 증가 실적도 만들지 않는다.
- 문제의 원인을 입증하는 과거 사실(기발주 14건의 승인 기록 등)은 만들지 않는다. 합성 속성은 판단에 쓰는 입력에만 붙인다.
- 원본에 있는 값과 어긋나는 합성값은 만들지 않는다.
- 모의 회신에는 입고 지연, 조기 공급 불가, 승인 거절, 회수일 추가 지연 등 불리한 경우를 포함한다.
- 리드타임 단축, MOQ 면제, 더마 증산 등 원본 제약을 바꾸는 값은 별도 시나리오로 두고 필요한 확인을 함께 적는다.

| 추가 정보 | 정보 성격과 처리 |
|---|---|
| 캠페인별 SKU 수요·판매 기간 | 마케팅 확인 요청에 대한 모의 회신. 수량의 전제·작성 주체·기준시점을 기록 |
| 입고 일정 초기값 | 발주일 + 리드타임으로 도출. 확정 납기가 아닌 미확인 추정값으로 표시 |
| 확정 납기·조기·분할·추가 공급 가능 여부 | SCM 또는 Corevia 공급 담당자의 모의 회신. 원본 제약과의 관계 기록 |
| 재무 재전망 확인 | 재무의 모의 확인 회신. 독립적인 계산 검증과 구분 |
| 입고 예정일·확정 여부(기발주, 운송 중 물량) | 합성 속성. 도출값(발주일 + 리드타임)과 같거나 늦게만 두고, 이른 값은 조기 공급이므로 별도 시나리오 |
| SKU 목표 재고 주수 | 합성 속성. 원본의 리드타임·안전재고 범위 안에서 정하고, 발주량 산식은 원본 정의를 사용 |
| 공급처 결제 조건(신규 발주 지급일) | 합성 속성. 원본 발주 14건의 지급일을 재현하는 값 하나로 두고 확인 요청에 연결 |
| 기안 묶음 ID | 합성 속성. 회의록이 25건을 한 기안으로 적은 것을 근거로 함 |
| 승인권자별 표준 결재 소요일 | 합성 속성(원본 근거 없는 가정값). 상신·회신 마감 역산에 사용 |
| 승인 요청·회신 | 요청은 시스템 생성 기록, 외부 승인·거절은 모의 회신 |
| 실행 중 사건·상태 이력 | 시스템이 실제 생성한 실행 기록. 입력이 모의라는 사실도 유지하며 실제 기업 운영 이력과 구분 |
| 기한 역산 일수·역할·상태 정의 | 운영 가정. 기존 승인권한과의 관계 설명 |

## 4. 자료별 설명 양식

새 합성 자료나 가정을 추가할 때 아래 양식을 작성하고 데이터에서 연결한다. 미확인 내용은 미확인으로, 아직 실행하지 않은 검증은 미실행으로 남긴다.

```markdown
### 자료명

- 자료 ID / 버전:
- 정보 성격: 합성 외부 회신 / 추가 가정 / 모의 매핑 / 기타
- 보완할 정보 공백:
- 영향받는 판단과 생성 목적:
- 이 보완 방법을 선택한 이유:
- 데이터 파일 위치:
- 연결 원본 파일·키·관계:
- 대상·단위·기간·규모:
- 기준시점·사건 발생일·적용일의 의미:
- 가상 작성·회신 주체와 담당 역할:
- 값·관계를 정한 방법과 가정:
- 적용할 원본 제약과 추가 제약:
- 기본 시나리오 / 대안 시나리오 구분:
- 실제 사용 위치와 영향받는 계획·작업·상태:
- 실제 작동 / 모의 처리 / 설계 단계 구간:
- 주요 조건 변경·불리한 입력의 검증 방법:
- 검증 상태·결과·실행 기록 위치:
- 결과 해석의 범위와 미확인 사항:
- 재현 절차·초기화 방법:
```

추가 행의 메타데이터는 아래처럼 둘 수 있다. 필드명은 구현에 맞게 바꿔도 된다.

| 권장 필드 | 의미 |
|---|---|
| `record_id` | 추가 행의 고유 식별자 |
| `effective_at` | 적용 시점 |
| `source_ref` | 원본 파일·행 키. 여러 원본이면 연결 목록 사용 |
| `generation_reason` | 해당 행의 생성 이유 |
| `data_kind` | 합성·가정·도출·시스템 생성 등의 정보 성격 |
| `occurred_at` | 사건 발생 시점. 적용 시점과 구분 |
| `scenario_id` | 기준 상황 또는 대안 시나리오 식별자 |
| `spec_ref` | 위 자료 설명과 버전을 찾을 수 있는 참조 |

원본에 직접 대응하는 행이 없으면 원본 키를 지어내지 않는다. 연결되는 파일·업무 대상과 직접 대응이 없는 이유, 매핑 가정을 설명한다. 원본의 `NONE` 코드 의미도 임의로 바꾸지 않는다.

## 5. 작성과 검증 순서

1. 원본에서 필요한 정보의 존재 여부를 확인하고 공백 또는 충돌을 기록한다.
2. 도출·확인 요청·가정·합성 중 방법을 정하고 선택 이유를 작성한다.
3. 자료 설명, 행 식별자, 원본 연결, 적용 시점, 시나리오를 정의한다.
4. 원본과 분리된 위치에 자료를 만들고 실제 처리에 연결한다.
5. 정상·주요 조건 변경·정보 부족 또는 승인 거절 사례를 실행한다. 변경과 정보 부족·거절 사례는 합칠 수 있다.
6. 모의 회신 이후 구현이 직접 판단·계획·작업·상태를 갱신하는지 확인한다. 결론이 유지되면 유지 근거를 기록한다.
7. 사용 자료·가정·업무 설계의 버전과 재실행 방법을 고정해 제출 설명에 연결한다.

### 완료 전 체크리스트

- [ ] 원본을 수정하지 않았고 추가 자료에서 원본까지 추적할 수 있다.
- [ ] 추가 행에 식별자·적용 시점·원본 연결·생성 이유가 있다.
- [ ] 원본 사실·부서 주장·가정·합성 입력·계산·실행 결과가 구분된다.
- [ ] 단위·기간·대상·규모·연결 기준과 값의 전제를 설명했다.
- [ ] 원본 제약 변경은 별도 시나리오이며 필요한 승인·전환 절차를 적었다.
- [ ] 실제 사용 위치와 모의 입력 이후의 상태 변경 증거가 있다.
- [ ] 불리한 입력이나 조건 변경을 검증했고 미실행 검증을 완료로 표시하지 않았다.
- [ ] 결과를 가정 아래의 결과로 표현하고 실제 기업의 증거·성과와 구분했다.
- [ ] 자료·가정·업무 설계 버전 및 데이터 로드·실행·결과 확인 방법이 있다.

합성 데이터나 별도 보고서를 추가 제출하도록 일괄 요구하는 것은 아니다. A04 §2의 데이터 설명표나 결과물 안에서 위 내용을 확인할 수 있게 하고 위치·링크를 안내해도 된다. 생성 모델명·프롬프트·난수 시드는 위 조항의 지정 필수 항목이 아니지만, 재현에 필요한 설정은 기록한다.
