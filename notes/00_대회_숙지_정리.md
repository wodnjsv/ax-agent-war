## 1. 미션 한 줄

**기업의 AI 기반 운영 시스템을 설계·구현하고 실제로 작동하는 모습을 보여준다.**
사건이 들어오면 → 정보 확인 → AI·사람이 대안 판단 → 승인 → 계획·작업·업무 상태가 **실제로 생성·갱신**되고, 그 결과가 다음 판단으로 이어져야 한다.

- 대상 기업: Aurora Holdings(지주) / Corevia Cosmetics(제조) / Masil Commerce(유통) / Celtonic Labs(인수 검토 대상, 자회사 아님)
- 개발 방식: Agentic coding 전제. 도구·언어·프레임워크 자유. 그래프 DB·Multi-Agent 강제 없음(선택 이유는 설명).
- 예선 1주일(제출 결과·실행 증거로 심사) → 본선(시연·조건 변경·질의응답). 일정·제출처는 별도 운영 공지.
- 프롬프트 기록·AI 기여 구분은 제출 불필요.

## 2. 완료로 인정되지 않는 것

- 지표·차트·BI 보고서, 정적 기획서, 권고문 생성만 있는 결과물
- 준비한 화면·결론을 순서대로 보여주는 시연 (화면에 예상 결과만 적어 둔 것)
- 부서명 나열·단순 통보로 처리한 "다른 부서 영향"
- 아이디어·도식·설명만 있는 "확장"
- 제약을 삭제해서 실행 가능하다고 주장하는 것, 유리한 회신만 가정한 성공 시연

## 3. 필수 요건 체크리스트

| # | 요건 | 충족 기준 |
|---|---|---|
| 1 | 핵심 업무 1개 완결 | 데이터 확인 → 판단 → 승인 → 후속 처리 → 상태 기록까지 연결 |
| 2 | 필수 전문성 확장 1개 이상 | 대표 업무의 **조회·계산·판단·상태 변경** 중 하나에 실제 사용. "없을 때 vs 있을 때" 차이를 실행 사례로 제시 |
| 3 | 다른 부서 영향 1개 이상 | 타 부서의 목표·제약을 식별하고 **대안 선택·승인·계획·후속 처리**에 실제 반영 (2번과 같은 사례로 충족 가능) |
| 4 | 정상 사례 1건 | 사건 입력 → 데이터·문서 확인 → 계산·판단 → 근거·대안 → 승인/후속 → 결과·상태 기록 |
| 5 | 변경 사례 1건 | 주요 조건·가정이 바뀌는 입력으로 기존 판단·계획 재검증. 결론 유지면 유지 근거 제시 |
| 6 | 정보 부족 또는 승인 거절 사례 1건 | 추가 확인·보류·재상신·대안 검토로 이어짐 (5번과 합칠 수 있음) |
| 7 | 구간 구분 | 실제 작동 / 모의 처리 / 설계 단계를 구간별로 표시 |
| 8 | 자료 구분 | 원본 기록 / 부서 주장 / 추가 가정·합성 / 계산·모의 결과를 구분 |

각 사례마다 설명할 것: 사용 데이터, 적용 시점, 주요 계산·가정, AI·사람·도구 역할, 변경 전후 차이.
외부 승인·발주·통지는 모의 처리 가능 — 단, 모의 회신을 받은 뒤 **구현이 직접** 판단·계획·상태를 갱신해야 실행 증거.

## 4. 운영 시스템의 6개 관점 (A01 §3)

| 관점 | 보여줄 증거 |
|---|---|
| 온톨로지(대상·관계·상태·규칙) | 관계·규칙이 실제 조회·판단·상태 연결에 쓰이는 사례 |
| 데이터의 의미와 연결 | 출처·단위·시점·연결 기준, 공백과 보완 방법 및 그 이유 |
| 분석과 대안 비교 | 계산·비교·가정·불확실성과 결론의 연결 |
| BI(판단을 돕는 화면) | 지표·경고·근거·대안을 보고 사용자가 **결정**할 수 있는 화면 |
| AI·사람·도구의 운영 역할 | AI의 입력·출력, 사람의 승인·예외 판단, 도구 실행과 상태 갱신 흐름 |
| 판단 이후의 처리 | 결정·회신에 따라 생성·갱신된 요청·계획·작업·문서와 이력 |

각각 별도 제품일 필요 없음. 한 구현 안에서 연결되면 됨.

## 5. 심사 관점 (A01 §7)

1. **기업 운영의 이해와 기획** — 누구의 어떤 결정을 개선하는가, 앞뒤 부서 목표·제약과의 연결, 확장의 필요성
2. **데이터에 근거한 판단** — 필요한 정보의 정의, 의미·관계·시점·한계 이해, 공백 처리의 일관성
3. **작동하는 운영 시스템** — 운영 중 AI 역할이 실제 판단·처리에 쓰이고 승인 이후 계획·작업·상태까지 이어지는가
4. **변경과 예외 대응** — 정보 부족·정정·거절 시 영향 확인과 계획 조정

세계관 크기·합성 데이터 양·모의 성과 수치는 평가 대상이 아님. 정보 정의의 이유, 업무 논리·제약의 타당성, 조건 변화 시 실제 처리가 평가 대상.
본선의 새 조건·정정·거절 회신은 **예선에서 선언한 구현 범위 안에서** 제시됨 → 범위 선언이 곧 본선 리스크 범위.

## 6. 제출물 (A01 §6, A04)

1. 문제·전문성 확장 요약 (결과물 이름, 사용자·의사결정, 현재의 어려움, 운영 안에서의 연결, 주업무 시작·종료, 본인 전문성, 필수 확장, 타 부서 목표·제약과 실제 반영, 개선 효과 확인 방법)
2. 업무모델과 데이터 설명 (객체·관계·상태·규칙, 승인권한, BPMN 변경점과 이유, 자료별 용도·단위·연결·보완 이유 표)
3. 대표 실행 사례 (정상 / 변경 / 정보 부족·승인 거절 — 입력·판단·후속 처리·실행 증거)
4. 추가 확장 목록 (필요성, 판단 개선, 연결, 구현 상태, 증거)
5. 실행·재현 방법 (소스 위치, 의존성, 데이터 로드, 대표 사례 입력·순서, 모의 회신 입력법, 결과 확인 위치, 초기화 항목)
6. 자기점검 16항목 (A04 §6)

## 7. 데이터 이용 기준 (A05)

**공통**
- CSV는 UTF-8, 첫 행 헤더, **파이프(`|`) 구분자**. 금액 KRW·VAT 제외. 제품 EA, 원료 kg. `NONE` ≠ 0.
- 달력: 월요일 시작, 월~금 영업일, 공휴일 없음. 사건의 발생일과 적용일은 따로 기록.
- **원본 폴더 보존.** 정제·매핑·확장 데이터는 별도 폴더, 원본 행·파일까지 추적 가능하게.
- 원본의 거래·계약·기한·품질·승인 정책 = 증거이자 제약. 부서 전망·회의 의견·분석값 = 주장.
- 원본 내 구판 대회 안내(3시간 제한, 배점, 프롬프트 로그, "고정 계산식 채점" 등)는 적용하지 않음. A01·A05 우선.

**스케일 (가장 중요한 함정)**
- 풀스케일(회사 실제 규모): `sku_inventory_ms`, `sku_weekly_sales_ms`, `sc_purchase_orders_ms`, `fin_cash_*`, `fin_*_aging_*`, 전속계약 28억
- 대표 표본: `mkt_orders_ms`, `mkt_returns_ms`, `mkt_coupons_ms`, `mkt_ad_spend_ms`, `mkt_traffic_inflow_ms`, `mkt_budget_plan_ms`
- 표본 성과를 전사 매출·현금과 합산 금지. 표본 비중 × 연간 예산 = 확정 손익으로 제시 금지. 결론은 비중·순위·방향까지.
- 수량·금액까지 연결하려면 대응표·규모·기간 가정을 별도 정의하고 **시뮬레이션 결과**로 표시. 근거 없으면 금액 효과는 판단 유보.
- SKU / 제품군 / 배치 / 로트 / 공장 / 라인은 서로 다른 집계 수준. 이름·코드 유사성만으로 1:1 가정 금지.

**W01 관련 계산 규칙**
- 재고 커버 = 현재고 / 최근 4주 평균 주간판매량 (원본 검산은 `on_hand_qty`만. 입고예정·예약 포함 지표는 새 이름으로 구분)
- 현금 전망 = 기초 + 예정 회수(AR `due_date`) − 예정 지급(AP 중 `po_id='NONE'`) − 발주대금(PO `payment_due_date`). **AP의 PO 연결분 이중 차감 금지.** 새 시나리오는 원본 전망 포함분과 추가 유출을 분리.
- 차입 약정: Masil **단독** 기준, **매 영업일** 일말 가용현금 30억 미만 여부. 기간 평균·그룹 지원 전제 불가.
- GMV는 쿠폰 반영 후. Net Revenue = GMV − 반품환불액. 공헌이익은 각 비용 한 번씩만 차감.
- `fin_cash_forecast_ms`(공식 전망) 등 기존 분석값은 부서 산출물 — 읽은 것만으로 검증 아님.

**확장 자료 관리**
- 합성은 선택. 보완 방법 4가지: 원본 도출 / 확인 요청 / 명시적 가정 / 합성. 선택 이유·사용 위치·검증 기록.
- 추가 행에는 식별자·적용 시점·원본 연결·생성 이유.
- 독점 공급·능력·계약·승인 제약을 바꾸는 가정은 기본 사실을 덮어쓰지 말고 **대안 시나리오로 분리**.
- 예선 제출 시 자료·가정·업무 설계의 **버전 기록** (본선은 그 범위를 기준으로 사건 적용).

## 8. BPMN 사용 원칙

- 제공 BPMN은 **교육용 현재 업무(as-is)**. 그대로 자동화할 의무 없음. 지연·중복·불필요한 전달을 찾아 재설계 가능.
- 재설계 시: 변경 이유와 추가 가정 설명, 원본 사실·제약·승인권한 존중, 없는 승인 절차를 추가하면 교육용 가정으로 표시하고 기존 권한과의 관계 설명.
- 개선한 단계가 **어떤 객체를 조회하고 어떤 상태를 바꾸는지** 설명.

## 9. W01 — 캠페인 수요와 공급 일정

**질문:** 캠페인으로 늘어날 주문을 재고·입고 일정과 함께 검토할 때, 어느 부서 사이에서 확인과 결정이 늦어지는가?

**As-is 흐름 [가정]**
`(마케팅) 캠페인 계획 공유 → (SCM) 재고·입고표 대조 → (재무) 금액·승인권한 검토 → (승인권자) 발주 승인? → 예: (SCM) 발주서 작성·전달 → 입고예정 회신 확인 → (마케팅) 일정표·발주 기록 정리 → 종료 / 아니오: 보류·재검토 종료`
- 파일과 회의로 검토하는 순차 흐름. 승인 분기는 사람의 별도 절차 결과.
- "보류·재검토" 종료는 이번 회차의 종료일 뿐 후속 확인 의무가 남음. "회신 기록" 종료는 판매 성공이 아님.

**원본에서 확인되는 단초 [원본]**
- 캠페인 이후 주문 급증·품절·긴급배송·반품 발생 (회의록)
- 평시 재고 발주는 SCM 승인. **현금 하회 예상 구간에 유출되는 신규 약정은 금액·종류 불문 그룹 CEO 승인이 우선** (평시 전결 권한은 그 구간에서 효력 상실)
- 판단 순서(정책): ① 재전망으로 하회 구간 특정 → ② 약정의 현금 유출일이 구간에 드는지 대조 → ③ 들면 그룹 상신
- 확정기한이 하회 구간보다 먼저 오는 건은 기한 전에 상신. 기한 경과 = 자동 확정 = 묵시적 승인.
- 재무팀은 매주 13주 현금 재전망 의무 (2026-04 이사회 결의)

**주최 측이 밝힌 미해결 지점**
1. 마케팅 표본 주문을 회사 전체 SKU 수요로 환산할 근거가 없다
2. 캠페인별 미래 수요 약속과 SKU·입고일을 연결한 계획표가 없다
3. 발주 변경 요청, 공급자 회신, 승인·미승인 결과의 사건 이력이 없다

**참가자가 정의할 영역:** 캠페인별 수요예측법, 적정 발주량, 자동화 방식.
**보완 예시(선택):** 캠페인별 SKU 수요 가정표(작성자·기준시점), 발주 변경 요청·공급자 입고예정 회신, 승인 요청·회신·보류 이벤트와 사유.

**관련 원본 파일**

`02_masil/`: master/m_campaign_ms, m_sku_ms · marketing/mkt_orders_ms, mkt_budget_plan_ms · inventory/sku_inventory_ms, sku_weekly_sales_ms, sc_purchase_orders_ms · financials/covenant_terms_ms, fin_cash_daily_ms, fin_ar_aging_ms, fin_ap_aging_ms, fin_cash_forecast_ms, lc0001_payment_term_notice

## 10. W01 원본 데이터로 확인한 사실 (2026-11-12 재계산)

### 10.1 현금 — 공식 전망과 재계산이 정반대 [계산]

정책이 지정한 방식(기초 51.48억 + AR `due_date` − AP `po_id='NONE'` − PO `payment_due_date`)으로 영업일별 재시뮬레이션:

| 일자 | 사건 | 일말 잔액 |
|---|---|---|
