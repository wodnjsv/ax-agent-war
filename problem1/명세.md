## 1. 범위와 접점

### 1.1 이 문제가 맡는 것

기안 25건마다 SCM이 공급 검토에 쓸 수 있는 수요 입력(증가율, 판매 기간)을 받아 버전으로 관리한다. 기준 수요 × 증가율로 SKU·주차별 추가 수량(EA)을 계산해 시뮬레이션 결과로 넘긴다. 문제 2는 이 값을 다시 계산하지 않는다(K1).

| 맡는 것 (사전 3.1) | 맡지 않는 것 (소유 문제) |
|---|---|
| `plan_sku_map` | 입고 일정, 재고 전개(주 격자, 시작 재고, 전개 끝 주), 잔여 여지, 공급 판정, 방향 판단, 대안 계산, 발주안 (문제 2) |
| `baseline_demand` (한 번만 계산) | 현금 구간, 약정 원장, 지급일, 승인 경로, `approval_anchor_date` (문제 3) |
| `demand_input`, `demand_input_sku_override` (구조화·검증·확인·등록·정정과 버전) | 사건 공통 형식·등록표, 확인 요청 `info_request`, 마감 `deadline_schedule`, 재검토, 보류, 미결, `plan_state` (문제 4) |

### 1.4 사전에 대한 이의 (문제 1 소유 정의, 보고만 함)

E1·E2는 사전 v1.1에서 수용됐다(3.1 `demand_input.version_status`, 5.1 `DEMAND_INPUT_REJECTED`). 남은 이의는 없다.

| # | 사전의 내용 | 이의 |
|---|---|---|
| E1 | `demand_status_by_plan.demand_status`의 열거값만 있고, 공급 판정이 가능한지의 기준은 없다 | 정정 회신을 확인하는 동안에는 `demand_status`=`확인대기`이면서 이전 `유효` 버전이 살아 있다(5.2). 판정 가능 여부는 `demand_status`가 아니라 "`version_status`=`유효`인 버전이 있는가"로 봐야 한다. 그래야 정정 확인 중에 기존 판정이 `판정불가`로 떨어지지 않는다. 사전 3.1에 이 기준을 적어 줄 것 |
| E2 | `DEMAND_INPUT_REJECTED` 뒤 재요청을 누가 내는지 적혀 있지 않다(`INFO_REQUESTED`는 문제 4 사건) | 문제 1 권고: 문제 4가 `DEMAND_INPUT_REJECTED`를 받아 `INFO_REQUESTED`(`request_kind`=`rerequest`, `caused_by`=반려 사건)를 낸다. 사전 5.4에 트리거로 적어 줄 것 |

v0.2 1.4에 적었던 불일치(EA 이중 계산, `uplift_pct` 단위, 버전·근거·작성자·기준 시점 필드 이름, 구성 이동 표현, 기준 수요 사건 이름)는 사전과 K1로 해소됐다.

- 처리: 요청 발행(`INFO_REQUESTED`)과 회신 기한은 문제 4가 한다. 문제 1은 그 요청에 붙는 화면 내용을 만든다.
  - 기안의 SKU와 SKU별 `baseline_weekly_qty`
  - 잔여 여지 요약(SKU × `inbound_scenario`, 문제 2 v2.0부터 `not_arrived` = 확약 입고만이 기준, `on_schedule` = 예상 입고 포함은 참고): 막을 수 없는 구간(문제 2 `reorder_reach_week` 이전 주)의 최소 `residual_headroom_qty`와 그 주, `base_only_shortfall.first_stockout_week`. 주별 전개는 문제 2 칸에 두고 여기서 반복하지 않는다. 문제 2 행에 `reorder_reach_week`가 없으면 전 구간 최소로 보이고 그렇게 표시한다. 문제 1은 값을 모으기만 하고 다시 계산하지 않는다
  - 참고 지표: 기안 배수와 표본 명목 ROAS(나란히), 표본 건수와 "표본 얇음" 표시(예: 더마 600건, 캠페인 1개), 전사 주간판매 최대/중앙값
  - 표시 문구: "증가율은 판매 기간 내 매주 같게 적용되며, 짧은 기간에 몰리는 캠페인의 정점 주 수요를 낮게 잡을 수 있음"(U3-3)
- 결과 상태: `demand_status`=`미입력`. `request_status`는 문제 4가 관리한다.

### 4.2 회신 수신 → 구조화 → 확인 → 등록

1. **수신**: `INFO_REPLIED`(`request_id`, `reply_text`, `reply_pattern`)를 받는다. 새 `version`을 `version_status`=`확인대기`로 만들고 `demand_status`=`확인대기`로 둔다.
2. **구조화(AI, OpenRouter)**
   - `reply_text`에서 `uplift_pct`, `sale_start_week`, `sale_weeks`, SKU별 조정값, 근거 문장을 뽑는다.
   - 원문에 없는 수치는 채우지 않고 `missing_fields`로 표시한다.
   - 프롬프트에 가상 일자와 기준 연도, SKU 이름을 넣는다. "08-17 주"처럼 연도만 빠진 표현은 날짜(그 주 월요일)로 바꾸고, "9월 하순"처럼 하나의 주로 정할 수 없을 때만 비운다.
   - 결과는 `DEMAND_INPUT_STRUCTURED`(`extracted_fields`, `missing_fields`)로 남긴다.
   - `OPENROUTER_API_KEY`가 없으면 이 단계를 건너뛰고 "AI 미연결"로 표시한다. 사건은 내지 않는다.
   - 자동 처리(모의 자료 S1)로 들어온 회신은 AI를 부르지 않는다. 자료의 확인된 값으로 바로 확인·등록하고, 회신 사건과 버전에 'AI 호출 없음(자동 처리)'을 남긴다. AI 구조화는 기안 담당자가 화면에서 자유 서술을 넣을 때만 부른다(사용자 결정 2026-11-15).
   - 담당자가 읽는 문장(AI의 불명확 사유·근거, 화면 응답의 비운 값, 반려 사유)은 업무 용어와 품목 이름으로 쓴다. 필드 코드·품목 코드는 화면 응답의 `missing_field_keys`, `extracted_fields`처럼 기계용 필드에만 둔다.
3. **검증(규칙)**
   - `uplift_pct` ≥ 0인 숫자
   - `sale_start_week`는 월요일이고 2026-07-06 이후
   - `sale_weeks`는 1 이상의 정수
   - 판매 종료 주(`sale_start_week` + (`sale_weeks` − 1)주) ≤ `projection_end_week`(2026-12-28)(사전 A2)
   - 조정값의 `sku_id`는 해당 기안의 `plan_sku_map` 안
   - 필수 항목 누락 없음
   - 09-28 주 뒤 구간은 반려하지 않는다. 문제 2가 `beyond_horizon`으로 표시한다.
4. **확인(사람)**
   - 마케팅 담당이 구조화 결과를 확인하고 필드를 확정한다. 시연에서는 S1의 가상 확인자 확정값이 들어간다.
   - AI 결과와 확정값이 다르면 다른 필드를 `changed_fields[]`로 기록한다(R8).
   - AI 미연결이면 확인자가 필드를 직접 입력한다. 확인 전에는 판정에 쓰이지 않는다.
5. **결과**
   - 검증 통과 + 확인 → 그 버전이 `유효`가 되고, 이전 유효 버전은 `대체됨`이 된다. 사건은 v1이면 `DEMAND_INPUT_REGISTERED`, v≥2이면 `DEMAND_INPUT_REVISED`(`origin`=`reply`, `changed_fields[]`)다. `demand_status`는 `등록됨` 또는 `정정됨`이다.
   - 검증 실패 또는 확인 거부 → `반려`, `DEMAND_INPUT_REJECTED`(`reject_reason`)를 낸다. 재요청 발행은 문제 4가 한다(1.4 E2). 이전 유효 버전이 있으면 그대로 유지한다.

### 4.3 추가 수량 계산 (시뮬레이션, K1)

```
applied_uplift_pct[sku] = override_uplift_pct[sku]  (있으면)
                        = uplift_pct                (없으면)

added_qty_ea[plan, sku, week_start] = round_half_up( baseline_weekly_qty[sku] × applied_uplift_pct[sku] ÷ 100 )
    for week_start in [sale_start_week, sale_start_week + (sale_weeks − 1)주]
```

- `uplift_pct`는 % 단위다. 35.0은 기준 수요의 35%를 뜻한다.
- 유효 버전이 생길 때마다 그 버전의 행을 만든다. 문제 2는 이 값을 다시 계산하지 않는다.
- 가정
  - 추가 수요는 SKU 기준 수요에 비례한다(R1). [가정]
  - 판매 기간 안에서는 매주 같은 증가율이다(U3-3).
  - 기준 수요는 기준일 이후에도 그대로다. 계절성은 넣지 않는다(78주 최대/중앙값 1.18~1.30배 [계산]). [가정]
  - 같은 SKU를 쓰는 기안의 추가분은 각자 기준 수요 위에 계산하고, 합산은 문제 2가 순서 규칙에 따라 한다.
- 표시: 모든 행에 `source_type`=`계산`, `is_simulation`=true를 붙이고 화면에 "시뮬레이션 결과"로 표시한다.
- 알려진 한계
  - 매주 같은 증가율은 CMP-0003처럼 짧은 기간에 몰리는 캠페인의 정점 주 수요를 낮게 잡을 수 있다(U3-3, 화면 표시).
  - 비례 배분은 표본 주문의 SKU 분포와 다르다.
  - 기준 수요가 과거 재고 부족으로 눌려 있었는지는 확인 불가다.

### 4.4 수요 입력이 없거나 늦을 때

- 요청 기한 경과(`request_status`=`기한 경과`), 기한 경고(`W1`), 재요청과 보류는 문제 4가 한다. 문제 1은 `demand_status`를 `미입력`으로 두고 판매 기간에 기본값을 넣지 않는다(R2).
- 수량과 무관하게 성립하는 방향 판단은 문제 2가 `supply_judgment.direction_note`로 낸다(U2-6). 문제 1은 요청 화면에 `stockout_weeks[]`를 계속 보여준다.
- 마감 후 회신이 도착하면 4.2와 같이 처리한다. 지연 여부와 소요 시간은 문제 4가 `occurred_at`과 `request_due_date`로 기록한다.
- 보류(`hold`)가 걸려 있으면 화면에 `hold_owner_dept`·`hold_due_date`·`resume_condition`을 함께 표시한다. 보류는 수요 입력 처리 규칙을 바꾸지 않는다.

### 4.5 대안 선택에 따른 새 버전

- `ALTERNATIVE_SELECTED`의 `alternative_selection` 중 `alternative_type`이 `시기이동` / `물량상한` / `구성이동`이면 새 `version`을 `origin`=`alternative`로 만든다.
  - `new_sale_start_week`, `new_sale_weeks`, `new_uplift_pct`, `new_override_uplift_pct[]` 중 들어온 값만 바꾸고, 나머지는 직전 유효 버전에서 이어받는다.
- `보충발주` / `조기분할요청` / `집행일이동`은 수요 입력을 바꾸지 않는다. 집행일 이동은 문제 2의 `plan_change`로 문제 3에 간다.
- 대안 값은 마케팅이 선택한 것이므로 확인 단계를 거친 것으로 보고 바로 `유효`로 둔다. 사건은 `DEMAND_INPUT_REVISED`(`origin`=`alternative`, `caused_by`=`ALTERNATIVE_SELECTED`의 `event_id`), `source_type`=`사람입력`이다.

### 4.6 재검토로 넘기는 것

- 새 유효 버전의 사건(`DEMAND_INPUT_REGISTERED` / `DEMAND_INPUT_REVISED`)이 트리거다. 그 기안과 같은 SKU 뒤 순번 기안의 공급 판정 재검토는 문제 4가 `REVIEW_OPENED`로 연다.
- `baseline_demand_version`이 바뀌면 `BASELINE_DEMAND_SET`을 내고, 그 버전을 쓴 모든 `campaign_demand_weekly`를 다시 계산한다. 원본 판매 기간이 고정이라 시연에서는 초기 1회만 발생할 것으로 본다.
- `review`(`target_type`=`demand_input`)를 받으면 결론은 내지 않는다. 그 기안의 `info_request`(`request_kind`=`correction`)가 문제 4에서 나가도록 응답한다. `payload.rejudge`=false면 이미 처리됐다는 뜻이므로 아무것도 하지 않는다(사전 5.4).

## 5. 사건과 상태 전이

### 5.1 사건 (사전 5절)

문제 1이 내는 사건:

| 사건 | 언제 | payload | `source_type` |
|---|---|---|---|
| `BASELINE_DEMAND_SET` | 기준 수요 계산·변경 | `baseline_demand_version`, `window_start`, `window_end` | `계산` |
| `DEMAND_INPUT_STRUCTURED` | AI 구조화 완료(확인 전). AI 미연결이면 내지 않음 | `demand_input_id`, `version`, `extracted_fields`, `missing_fields` | `계산` |
| `DEMAND_INPUT_REJECTED` | 검증 실패·확인 거부 | `demand_input_id`, `version`, `reject_reason` | `계산` / `사람입력` |
| `DEMAND_INPUT_REGISTERED` | v1 유효 | `demand_input_id`, `version` | `사람입력` |
| `DEMAND_INPUT_REVISED` | v≥2 유효(정정 회신 또는 대안) | `demand_input_id`, `version`, `origin`, `changed_fields[]` | `사람입력` |

문제 1이 받는 사건: `INFO_REQUESTED`, `INFO_REPLIED`, `REVIEW_OPENED`, `HOLD_PLACED` / `HOLD_RESUMED` / `HOLD_CANCELLED`(문제 4), `SUPPLY_PROJECTED`, `ALTERNATIVE_SELECTED`(문제 2)

- 시연의 사람입력은 모두 가상이므로 `is_synthetic`=true다. `is_simulation`은 사전 2.1 규칙을 따른다.
- `plan_sku_map`과 `campaign_demand_weekly`는 사건이 아니라 버전이 있는 자료다. 사건은 `premise_refs`로 가리킨다.

### 5.2 상태

`demand_status_by_plan.demand_status` (요청 상태 `request_status`는 문제 4 소유):

```
미입력 ──INFO_REPLIED──▶ 확인대기
확인대기 ──검증 통과·확인 (DEMAND_INPUT_REGISTERED)──▶ 등록됨(v1)
확인대기 ──반려 (DEMAND_INPUT_REJECTED)──▶ 미입력 (유효 버전이 없을 때) / 직전 상태 (유효 버전이 있을 때)
등록됨·정정됨 ──정정 회신 INFO_REPLIED──▶ 확인대기 (유효 버전은 유지) ──확인 (DEMAND_INPUT_REVISED)──▶ 정정됨(v+1)
등록됨·정정됨 ──ALTERNATIVE_SELECTED(시기이동·물량상한·구성이동)──▶ 정정됨(v+1)
```

- 공급 판정에 쓰이는 것은 `version_status`=`유효`인 버전뿐이다. 유효 버전이 없으면(미입력, 첫 회신의 확인대기) 문제 2는 `판정불가`로 둔다. 정정 확인 중인 확인대기에서는 기존 유효 버전으로 판정이 유지된다(1.4 E1).
- `demand_input.version_status`: `확인대기` → `유효` → `대체됨`, 또는 `확인대기` → `반려`

## 7. 확인 불가 항목과 확인 요청

확인 요청은 문제 4가 `INFO_REQUESTED`로 발행한다. 아래 요청 중 S1 외의 회신은 합성하지 않으므로, 회신이 오지 않은 요청은 문제 4에서 미결로 남는다.

| 확인 불가 항목 | 영향 | 확인 요청 (대상 · 내용) |
|---|---|---|
| 마케팅 내부 수요 예측이 있는지와 그 내용 | 모의 증가율을 실제 판단으로 볼 수 없음 | `MKT` · 수요 입력 요청에 "근거 자료 유무와 작성 시점" 항목 포함 |
| 기안 배수 9.17 / 10.42 / 11.25의 산정 근거 | 예상 GMV를 수요 근거로 쓸 수 없음 | `MKT` · 배수 산정 방법 |
| `settlement_date`와 판매 시점의 관계, 계약 확정과 판매 시작의 선후 | 판매 기간에 기본값을 둘 수 없음. `settlement_date`가 `contract_deadline`보다 앞서는 기안이 있음(PLAN-007 등) [계산]. 미승인 상태로 집행 예정일이 지나는 경우도 확인 불가(U3-4, 문제 3·4가 경고와 `settlement_unapproved` 확인 요청) | `MKT` · 집행 예정일의 의미와 판매 시작 예정일 |
| 국가별 가용 재고 | 해외 캠페인 수요를 전사 재고로 받을 수 있는지 | `SCM`(문제 2 영역) · 국가·창고별 재고 구분 유무 |
| 과거 판매가 재고 부족으로 눌렸는지 | 기준 수요가 실제 수요보다 낮을 수 있음. 특히 더마(원본 커버 2.2~4.3주) | `SCM` · 과거 품절 주차 기록 |
| 캠페인이 전사 판매를 실제로 얼마나 늘렸는지 | 증가율의 검증 수단이 없음 | `MKT` · 전사 기준 캠페인 성과 자료 유무. 회신을 합성하지 않음(U2-2a) |
| 마케팅이 SKU별 차등을 줄 근거가 있는지 | 비례 배분이 실제와 다를 수 있음 | `MKT` · S2 조정값 요청에 포함 |

`request_topic`의 사전 열거값에는 수요 입력(`demand_input`) 외에 위 항목에 맞는 값이 없다. 위 요청은 `demand_input` 요청의 부속 질문으로 넣거나 `source_unknown`으로 낸다. 어느 쪽인지는 문제 4가 정한다.

### 9.3 사건

- 구독: `INFO_REPLIED`(문제 1이 낸 것, 또는 문제 4 요청 중 `request_topic=demand_input`인 것 → 확인대기 버전), `ALTERNATIVE_SELECTED`(`시기이동`·`물량상한`·`구성이동` → 새 버전), `REVIEW_OPENED`(`target_type=demand_input`이고 `rejudge`≠false → 문제 4 `requestInfo`로 `correction` 요청). 요청 상태·마감·보류는 사건 대신 문제 4 expose로 읽는다.
- 발행: `BASELINE_DEMAND_SET`(초기화), `INFO_REPLIED`(수요 회신 전달), `DEMAND_INPUT_STRUCTURED`, `DEMAND_INPUT_REJECTED`, `DEMAND_INPUT_REGISTERED`, `DEMAND_INPUT_REVISED`. AI 기록 `AI_CALL_RECORDED`·`AI_OUTPUT_REVIEWED`는 `ctx.ai.call`·`ctx.ai.review`가 남긴다(`ai_task_name`=`demand_reply_structure`).
- 첫 유효 버전은 `DEMAND_INPUT_REGISTERED`, 그 뒤 유효 버전은 `DEMAND_INPUT_REVISED`다. 첫 회신이 반려되고 두 번째 회신이 처음 유효가 되면 v2라도 `REGISTERED`다.

### 9.4 화면·경로 (`/api/p1/...`)

`GET /plans/:plan_id`(요청 화면 내용), `POST /plans/:plan_id/replies`, `POST /demand-inputs/:demand_input_id/versions/:version/confirm`, `POST /preview`, `GET /plan-sku-map`, `GET /baseline-demand`, `GET /campaign-demand-weekly`, `GET /demand-status`, `GET /mock`, `POST /mock/:record_id/deliver`. 패널(`problem1/src/panel.js`)은 기안 상세에 ① 기안-SKU 대응·기준 수요, ② 수요 입력 요청, ③ 회신·구조화·확인, ④ 추가 수량(EA) 네 칸을 그리고, 모의 입력 화면에 S1 전달 버튼을 둔다.

### 9.5 마케팅 기안 담당자 화면용 API와 평가자 화면용 설명 카드 (사용자 결정 2026-11-15)

주 사용자는 마케팅 기안 담당자다. 왼쪽 업무 화면은 아래 경로로 수요 입력·정정을 하고, 오른쪽 평가자 화면은 `describeEvent`로 사건을 풀어 쓴다. 계산·판정 규칙은 바꾸지 않았다.

| 경로 | 요청 | 응답 |
|---|---|---|
| `GET /api/p1/entry/:plan_id` | — | 입력 화면 한 번에: `plan`(원본 기안), `status`, `deadline`(수요 입력 마감·확정기한), `request`(문제 4 최근 요청), `current`(유효 버전 + SKU별 추가 수량 `added_qty_by_sku[]`·합계), `pending`(확인 대기 버전: 원문, AI 상태, 뽑은 값, 비운 값, 비운 이유), `history`, `reference`(SKU별 이름·기준 수요·막을 수 없는 구간 잔여 여지(두 입고 경우)·품절 첫 주·정기 보충 시작 주, 표본 참고), `input_rules`, `actions`(`mode` 최초 입력/정정, 입력 가능 여부, 확인 대상, 종결 사유) |
| `POST /api/p1/entry/:plan_id/text` | `{ reply_text }` | 자유 서술 → `INFO_REPLIED`(사람입력) → AI 구조화(연결 시) → 확인 대기. `{ result, entry }` |
| `POST /api/p1/entry/:plan_id/confirm` | `{ version, decision: 확인/거부, fields: { uplift_pct, sale_start_week, sale_weeks, overrides[], rationale_text } }` | 검증 → 등록·정정 또는 반려 사유. `{ result, entry }` |
| `POST /api/p1/entry/:plan_id/direct` | `{ fields }` | AI 없이 값 직접 입력·정정(확인대기 → 즉시 확인). `{ result, entry }` |
| `POST /api/p1/preview` | `{ plan_id, sale_start_week, sale_weeks, uplift_pct, override_uplift_pct[] }` | 저장 전 추가 수량 미리보기 |
| `GET /api/p1/describe/:event_id` | — | `{ event_id, card }` |

- 확정·기한 경과 확정·철회된 기안(문제 4 `plan_state`)은 입력 경로가 409를 돌려준다.
- 공개 함수 추가: `describeEvent(event)`, `entryView(plan_id)`, `enterDirect({ plan_id, fields })`.
- `describeEvent`가 다루는 사건: `BASELINE_DEMAND_SET`, `INFO_REQUESTED`(`request_topic=demand_input`), `INFO_REPLIED`(문제 1이 낸 것), `DEMAND_INPUT_STRUCTURED`, `AI_CALL_RECORDED`·`AI_OUTPUT_REVIEWED`(문제 1의 수요 회신 구조화), `DEMAND_INPUT_REGISTERED`, `DEMAND_INPUT_REVISED`, `DEMAND_INPUT_REJECTED`. 그 밖에는 `null`이다.
- 카드 형식: `{ title, actor_kind, actor_label, inputs[{label, value, source, ref}], rule, result, next }`.
  - 모의 자료(S1)·기본 모의 입력으로 들어온 값은 `모의 입력`, 화면에서 넣은 값은 `사람`이다.
  - 등록·정정 카드의 `result`에는 SKU별로 "기준 수요 × 증가율 = 값 → 주당 EA × 주수 = 합계"를 실제 수치로 적는다.
  - 구조화 카드에는 원문, 뽑은 값, 비운 값과 비운 이유를 적는다.
