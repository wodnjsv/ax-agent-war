## 0. 공급 확약·원료·생산 제약 반영 — 최소 변경 계획과 검증 기준 (v2.0, 사용자 요청 2026-11-15)

목표: 캠페인 상품을 필요한 날짜까지 확보할 수 있는지 판단한다. 내부 발주 승인(지출 허용)과 Corevia 공급 확약(수량·납기 약속)과 입고 완료를 구분하고, 공급 조건이 바뀌면 기안을 다시 판정한다.

**바꾸는 것**
1. 입고 행 상태 `supply_status`: `예상`(공급 확인 대기) / `확약` / `입고 완료`(확약 행의 도착일이 지남, 조회 때 표시) / `미확약 잔량`(부분 공급의 남은 양) / `공급 불가`. 승인된 발주안은 발주 예정일 + 리드타임의 `예상` 입고로만 들어간다(종전: `확정`). 기존 입고 회신 S2-ETA의 확정·지연은 `확약`, 미회신은 `예상`이다.
2. 판정: 확약 입고만으로 성립하면 `가능`. 예상 입고에 기대야 성립하면 `조건부`이고 조건 종류는 행의 출처로 나눈다 — 기발주·운송 중 `inbound_unconfirmed`(종전), 캠페인 발주안 `supply_commitment_pending`(공급 확약 대기, 새), SCM 정기 보충 `baseline_replenishment_unconfirmed`(새). 판정 구간 전체(막을 수 없는 구간과 보충 가능 구간)에서 본다. 승인으로는 조건이 풀리지 않고 Corevia 확약 회신으로만 풀린다.
3. Corevia 공급 회신 `supply_commitment`(합성 자료 S2-CVC): 대상 발주안·기발주, 요청 수량·필요 도착일, 공급 가능 수량·도착 예정일, 원료 확보 여부·가용일·근거, 생산 라인 배정·완료 예정일, 검사·운송 조건, 산정 근거, 회신자·기준 시점·버전·근거 자료, 상태(`가능`/`부분 가능`/`불가`/`미확인`)와 검증 결과(`정상`/`확인 필요`). 필수 값이 비면 추측하지 않고, 날짜·수량·조건이 모순되면 `확인 필요`로 입고를 바꾸지 않는다. 부분 공급은 확약 수량 행과 미확약 잔량 행으로 나누고 원래 발주 수량을 덮어쓰지 않는다. 같은 회신(`record_id`)의 재처리는 아무것도 바꾸지 않는다. 정정은 새 버전이다.
4. 회신 → 입고 일정 새 버전(`INBOUND_SCHEDULE_REVISED`) → 영향 기안 재판정(`SUPPLY_JUDGED`, 원인 = 회신 사건) → 대안 재계산 → 문제 4 재검토. 불가·부분 가능이면 그 발주안에 기대던 기안·SKU의 보충 발주를 막아(종전 승인 거절과 같은 처리) 남은 부족이 대안(연기·축소·구성 변경·철회)으로 간다.
5. 기준 수요 정기 보충 가정(S2-BLC, `covered_from_week`)을 없앤다. 기준 수요는 전 구간에서 재고를 깎는다. SCM 기준 수요 보충 계획 회신(합성 자료 S2-SCM-BR: SKU, 수량, 발주 예정일, 도착 예정일, SCM 확인 여부, Corevia 확약 여부)에서 SCM이 확인한 행만 입고에 넣는다(확약이면 `확약`, 아니면 `예상`). 보충 계획이 확인되지 않은 SKU는 판매 기간 뒤의 부족(캠페인이 앞당긴 기존 수요 품절)을 `baseline_replenishment_unconfirmed` 조건으로 남긴다. 이 시스템은 기준 수요용 발주를 만들지 않고, SCM 정기 발주의 금액·지급일은 자료에 넣지 않는다(지어내지 않음). 그 현금 유출이 재전망에 없다는 한계를 화면에 적는다.
6. S2-SUP-REPLY 사유 문장의 C-201을 '입찰 기회(확정 수주·생산 배정 아님)'로 고친다.
7. 사건 이름은 기존 등록표를 쓰고 payload를 넓힌다(`SUPPLIER_REPLIED.payload.supply_commitment`, `INBOUND_SCHEDULE_REVISED.payload.changed_rows[].supply_status`).

**안 바꾸는 것**: 막을 수 없는 구간(판정일 + 7영업일 + 리드타임)과 연결 발주안 도착 주 예외, 부족·보충 발주 필요 판정, SKU 단위 캠페인 발주안 수량(캠페인 추가분 + MOQ 올림), 누적 순서, 대안 계산, 같은 날 묶기, 원인·사유 기록, 공개 함수 이름. Corevia의 원료·생산 일정을 이 시스템이 계산하지 않는다(회신 값을 받아 검증·연결만 한다). 승인권자의 위험 수용 기록·확정 가능 규칙은 문제 4 몫이다.

### 4.2 재고 전개

**주 격자와 시작 재고 (O1, O2)**
- 주는 `week_start`(월요일)로 표시한다. 첫 전개 주는 2026-07-06이고, 06-30 스냅숏 `on_hand_qty`를 그 주의 기초 재고로 둔다.
  - 한계: 스냅숏(화요일)과 06-29 주 실적의 경계가 맞지 않는다. 06-30 이후 그 주의 소진이 스냅숏에 반영됐는지는 확인 불가다.
- `projection_end_week` = 2026-12-28(26주).
  - 09-28 주 뒤 행은 `beyond_horizon=true`다.
  - 근거: 집행 예정일이 09-23까지 있고 판매 기간은 원본에 없어, 13주 안에서 판매가 끝나지 않는 기안을 거르지 않도록 늘렸다.
  - 판매 종료 주가 이 값을 넘는 입력은 문제 1이 반려한다(사전 A2).

**전개 식**

```
opening[sku, 2026-07-06] = on_hand_qty (06-30 스냅숏)
avail[w]     = opening[w] + Σ qty (arrival_week_start = w)
demand[w]    = baseline_weekly_qty + Σ added_qty_ea[plan, sku, w]     # 앞 순번 기안까지, campaign_demand_weekly (K1)
served[w]    = min(avail[w], demand[w])
unmet_qty[w] = demand[w] − served[w]                                   # 0보다 크면 "0 아래로 감" (U3)
projected_on_hand_qty[w] = avail[w] − served[w]
opening[w+1] = projected_on_hand_qty[w]
projected_cover_weeks[w] = projected_on_hand_qty[w] ÷ baseline_weekly_qty   # 원본 stock_cover_weeks와 다른 지표 (R1)
```

- `inbound_scenario`(K8):
  - `on_schedule`: 모든 입고 행을 `eta_date`대로 반영
  - `not_arrived`: 확정된 입고만 반영. 미회신 행은 전개 기간 안에 오지 않는 것으로 둔다
- [가정] 품절 주의 미충족 수요는 이월하지 않는다(판매 손실). 문제 정의 문서의 커버 전망과 같다.
- [가정] 시스템이 만든 발주안 외의 보충발주는 넣지 않는다. 앞으로 예정된 보충발주는 확인 불가다. 그래서 전개에는 보충으로 막을 수 있는 품절도 나타난다. 판정은 아래 구간 구분으로 이를 '부족'에서 뺀다.

**막을 수 없는 구간과 보충 가능 구간 (조정자 확정 (1))**
- SKU마다 판정일(`sim_clock`)에 `reorder_reach_week`를 구한다.
  - `reorder_reach_week` = (판정일 + 7영업일 = 발주 예정일, K5) + `lead_time_weeks`가 속한 주
  - (v2.0) 기준 수요는 전 구간에서 재고를 깎는다. v1.2의 정기 보충 가정(S2-BLC, `covered_from_week`)은 없앴고, SCM이 확인한 보충 계획 행(S2-SCM-BR)만 입고로 들어간다(4.8).
  - 기안별 예외(v1.1): 그 기안이 이어진 승인 전 SKU 발주안이 있고 오늘 ≤ 그 `planned_order_date`이면, 그 발주안 도착 주(`planned_order_date` + 리드타임)와 위 값 중 이른 주를 쓴다. 이미 만든 발주안이 제때 도착하는데도 날짜 경과만으로 '부족'이 되지 않게 한다.
  - 그 주보다 앞의 주는 `supply_window = unpreventable`(지금 발주해도 막을 수 없음)다.
  - 그 주부터는 `supply_window = reorder`(보충 발주로 막을 수 있음)다.
  - `reorder_reach_week`가 전개 끝 뒤면 전 구간이 `unpreventable`이다.
- 07-01 기준값 [계산]:
  - 색조(리드타임 6주): `unpreventable`이 ~08-10 주, 보충 가능 08-17 주부터
  - 기초·선케어·헤어·바디(8주): ~08-24 주, 08-31 주부터
  - 더마(12주): ~09-21 주, 09-28 주부터
- 판정일이 바뀌면 구간도 옮겨진다. 그래서 `onDay`에서 바뀐 기안만 다시 판정한다.
- [가정·한계] 증가율은 판매 기간 안에서 매주 같다(U6). CMP-0003처럼 짧은 기간에 주문이 몰리는 캠페인의 정점 주 부족을 과소평가할 수 있다. 판정 화면과 상신 첨부에 함께 표시한다.

### 4.3 누적 순서와 잔여 여지

- 순서(C5, O3):
  1. `plan_status` ∈ {`확정`, `기한 경과 확정`}인 건
  2. `contract_deadline`
  3. `settlement_date`
  4. `plan_id`
  - `철회` 건은 누적에서 뺀다. 규칙 버전은 `ordering_rule_version`이다.
- 기안 k의 판정은 순번 1..k−1의 `added_qty_ea`를 이미 얹은 전개 위에서 계산한다. 유효 수요 입력이 없는 앞 순번 기안은 추가분 0으로 둔다.
- `residual_headroom_qty[plan k, sku, w, inbound_scenario]` (조정자 확정 (1)):
  - w가 `unpreventable` 구간이면 min over v ∈ [w, `reorder_reach_week` 직전 주] of `projected_on_hand_qty[sku, v]`다(앞 순번까지 반영, 기안 k 추가분 0, 0 아래는 0).
  - w가 `reorder` 구간이면 `null`이다. 보충 발주로 확보하는 구간이라 상한을 두지 않고, 추가분이 이 구간 부족을 늘리면 조건부(`reorder_required`)가 된다.
  - 뜻: 막을 수 없는 구간에서, w주부터 기안 k가 더 얹어도 앞선 수요에 새 품절을 만들지 않는 누적 수량의 상한이다.
  - 행마다 `supply_window`를 붙인다. 두 입고 경우 모두 넘긴다(K8). 문제 1은 이 값의 경계에 맞춰 합성 `uplift_pct`를 배치한다(A4).
- `base_only_shortfall`: 모든 기안 추가분이 0일 때의 품절.
  - 전 구간 값: `first_stockout_week`, `recovery_week`, `stockout_weeks[]`(참고)
  - 배경 제약: `reorder_reach_week`, `unpreventable_end_week`, `first_unpreventable_stockout_week`, `unpreventable_stockout_weeks[]`, `unpreventable_shortfall_ea`. 막을 수 없는 구간의 기존 수요 품절이다. 캠페인이 그 주에 판매되거나 그 주보다 앞서 판매되면 `부족`이 된다.
- `supply_projection_base` 행에도 `supply_window`를 붙인다.
- 앞 순번 기안의 수요·순서·상태가 바뀌면 같은 SKU에서 뒤 순번 기안의 판정이 다시 열린다. `review` 생성은 문제 4가 한다.

### 4.4 공급 판정 `supply_judgment`

입력: 유효 `demand_input`, `campaign_demand_weekly`(문제 1), 두 입고 경우의 전개, 누적 순서, SKU별 `reorder_reach_week`(4.2). 평가는 `sale_start_week`부터 한다.

```
diff[sc, w] = unmet_qty(이 기안까지)[sc, w] − unmet_qty(앞 순번까지)[sc, w]     # 캠페인 때문에 늘어난 부족, w ≥ sale_start_week
U_on = { w < reach : diff[on_schedule, w] > 0 }     # 막을 수 없는 구간, 모든 입고 반영
U_na = { w < reach : diff[not_arrived, w] > 0 }     # 막을 수 없는 구간, 확정 입고만
P_on = { w ≥ reach : diff[on_schedule, w] > 0 }     # 보충 가능 구간
```

| `supply_verdict` | 조건 |
|---|---|
| `판정불가` | 해당 기안의 `version_status=유효`인 `demand_input`이 없다 |
| `부족` | `U_on`이 비어 있지 않다. 지금 발주해도 막을 수 없는 구간에서 캠페인이 부족을 늘린다 |
| `조건부` | `U_on`은 비었고, 아래 조건이 하나 이상이다<br>- `inbound_unconfirmed`: `U_na`가 비어 있지 않다(미확정 입고가 와야 막을 수 없는 구간이 버틴다)<br>- `reorder_required`: `P_on`이 비어 있지 않다(캠페인 때문에 필요한 보충 수량이 는다) |
| `가능` | 셋 다 비었다 |

- 부족 수량·주의 출처:
  - `부족`: `U_on`의 주와 `diff` 합. `shortage_qty_base_ea` = 같은 구간(판매 시작 ~ reach 직전)의 앞선 수요 부족.
  - `조건부`: 미확정 입고 조건이 있으면 `U_na` 기준, 없으면 `P_on` 기준이다.
  - 기안 행의 `shortage_qty_campaign_ea`는 가장 나쁜 판정을 받은 SKU들의 합이다.

- 기안 판정 = 그 기안이 쓰는 SKU 판정 중 가장 나쁜 값이다(부족 > 조건부 > 가능). SKU 행과 기안 행(`sku_id` 비움)을 함께 남긴다.
- 부족 수량·주의 출처:
  - `부족`이면 `on_schedule` 값이다.
  - `조건부`이면 `on_schedule`의 캠페인 부족이 0이므로 `not_arrived` 값이다.
  - 기안 행의 `shortage_qty_campaign_ea`는 가장 나쁜 판정을 받은 SKU들의 합이다.
- `condition_basis[]` (R3): 조건부의 조건 목록이다. 행마다 `condition_type`과 `sku_id`가 있다.
  - `inbound_unconfirmed`: SKU당 하나. {`inbound_row_id`, `source_ref`, `eta_date`}(가장 먼저 도착하는 행), `inbound_rows[]`{`inbound_row_id`, `source_ref`, `eta_date`}(막을 수 없는 구간의 마지막 부족 주까지 도착하는 미회신 입고 전부).
  - `reorder_required`: {`additional_reorder_qty_ea`(= `P_on`의 `diff` 합), `needed_by_week`(`P_on` 첫 주), `reorder_reach_week`, `order_deadline`, `order_deadline_passed`, `covered_by_approved_qty_ea`, `uncovered_qty_ea`, `po_draft_id`, `po_draft_status`, `po_draft_preview`{`order_qty`, `draft_version`, `planned_order_date`, `expected_arrival_week`, `amount_krw`, `arrives_before_gap`}}.
    - 조건은 그 SKU의 발주안(SKU 단위, 4.6)을 가리킨다(조정자 E (1)). 판정을 낼 때 그 SKU의 열린 발주안에 이 기안을 잇고, 없으면 만든다(`PO_DRAFT_CREATED`).
    - 발주안은 문제 3이 지급일·경로를 정해 상신한다. 승인되면 입고에 들어가 조건이 풀린다.
    - 승인된 발주안(승인 회신 또는 발주)은 확정된 약속이다(조정자 D2 (가)).
      - 발주 예정일 이전에 승인되면 그때 바로 입고 일정에 `eta_status=확정`, `eta_date` = 발주 예정일 + 리드타임으로 넣고 `INBOUND_SCHEDULE_REVISED`를 낸다. 발주 예정일에는 상태만 `발주`로 바꾼다.
      - 취소하지 않는다. 기안이 철회돼도 마찬가지다.
    - SKU 단위 누적(조정자 G (3), F (2) "승인된 발주 수량이 캠페인 추가 필요량 이상이면 충족"):
      - 승인 캠페인 발주안은 입고 일정에 들어가 있다(v2.0부터는 Corevia 확약 전 `예상`이라 확약 전에는 `supply_commitment_pending` 조건이 붙는다). 그래서 전개가 곧 SKU 누적 비교다. 앞 순번 기안들의 캠페인 추가분을 채우고 남은 승인 물량(MOQ 올림분 포함)이 그대로 뒤 기안의 캠페인 추가분을 채운다(누적 순서 4.3).
      - `additional_reorder_qty_ea`(= `uncovered_qty_ea`) = 승인 발주안까지 반영한 전개의 보충 가능 구간 캠페인 부족(남은 필요량). 0이면 조건 충족이다.
      - `campaign_need_ea` = 승인 캠페인 발주안 입고를 뺀 전개로 본 필요량. `covered_by_approved_qty_ea` = `campaign_need_ea` − `additional_reorder_qty_ea`(승인 물량이 덮은 양).
      - 남은 필요량만 SKU의 열린 초안에 이 기안 몫으로 들어간다(4.6).
      - 이력: v1.0의 'SKU 승인 풀을 순번대로 나눔'은 정기 보충 없는 전개에서 기준 수요가 남는 물량을 먹은 뒤에도 풀로 덮었다고 보아 PLAN-009 SKU-4001이 날짜 경과로 '부족'이 됐다(S-CEO-FLOOR 08-06). v1.1은 자기 몫만 세어 막았지만 발주안이 기안마다 늘었다. v1.2는 정기 보충 가정으로 전개와 범위의 전제를 맞춰 둘 다 없앴다.
      - SKU 행에는 `reorder_need`{`kind`, `additional_reorder_qty_ea`, `needed_by_week`, `campaign_need_ea`, `covered_by_approved_qty_ea`}를 남긴다(남은 필요량이 있을 때).
        - `kind=condition`: 보충 발주 필요 조건에서 나온 필요량.
        - `kind=shortage`: `부족` SKU의 보충 가능 구간 몫(`P_on`과 같은 계산). 그 기안이 `보충발주` 대안을 골랐을 때만 발주안에 들어간다.
        - 이미 열린 발주안에 이어진 기안의 SKU가 날짜 경과 등으로 `부족`이 되면 발주안에서 빼지 않는다(D2 (가): 부족이 되어도 보충은 여전히 필요). 보충 가능 구간 몫이 남아 있으면 그 양, 없으면 그 발주안의 이 기안 몫을 그대로 둔다.
    - 거절(조정자 E (2)): 기대던 발주안이 `APPROVAL_REPLIED` 거절로 `반려`되면, 그 발주안의 `linked_plan_ids` 기안·SKU는 보충 발주가 막힌다(`reorder_blocked`{`po_draft_id`, `approval_event_id`}, 기안 행은 목록).
      - 막힌 SKU는 막을 수 없는 구간을 판매 기간 끝 주까지로 늘리고 `reorder_required`를 만들지 않는다. 그래서 판매 기간 안의 캠페인 부족이 있으면 `부족`이다.
      - 판매 기간 뒤의 부족(캠페인이 앞당긴 기존 수요 품절)은 정상 보충 주기의 몫으로 보고 이 기안의 판정에 넣지 않는다 [가정]. 전개 끝까지 넣으면 기존 수요가 전개 안에서 바닥나는 SKU는 증가율 0.1%도 부족이 되어 물량상한이 늘 0이 된다.
      - 거절 회신을 원인(`caused_by`)으로 막힌 기안을 바로 다시 판정한다. 부족이면 대안을 다시 계산한다(4.5). 거절된 발주안은 다시 쓰지 않는다.
    - `order_deadline`(발주 시한): 이 날까지 발주해야 `needed_by_week` 주에 도착한다. 값은 그 주 금요일 − 리드타임이다. 화면에 표시한다.
  - 승인 회신이 `공급조건부수용`으로 이 판정을 지목해야 문제 4가 확정 가능으로 본다(C7).
- `preventable_by_reorder` (A2): `shortage_weeks[]`가 모두 `reorder_reach_week` 이후이면 true다. 곧 `reorder_required`만 있는 조건부다.
- `stock_warning`, `safety_breach_weeks[]`: 판매 기간 중 `projected_on_hand_qty` < `safety_stock_weeks_min × baseline_weekly_qty`인 주(`on_schedule`)다. 판정에 쓰지 않는다(U3).
- `direction_note` (U4): `판정불가`에도 낸다.
  - 막을 수 없는 구간의 기존 수요 품절이 있으면 그 주와 구간 끝을 적는다. 판매 기간이 그 주를 포함하거나 그보다 앞서면 증가율과 무관하게 `부족`이다.
  - 없으면 "그 구간의 잔여 여지 안이면 부족이 아니다"라고 적는다.
  - 보충 가능 구간에만 품절이 있으면 "추가분이 이 구간 부족을 늘리면 조건부(보충 발주 필요)"라고 함께 적는다.
- 필드(사전 3.2 `supply_judgment`):
  - 식별: `supply_judgment_id`, `supply_judgment_version`, `plan_id`, `sku_id`
  - 판정: `supply_verdict`, `first_shortage_week`, `shortage_weeks[]`, `shortage_qty_base_ea`, `shortage_qty_campaign_ea`, `preventable_by_reorder`, `condition_basis[]`, `stock_warning`, `safety_breach_weeks[]`, `direction_note`
  - 순서와 범위: `plan_order_rank`, `beyond_horizon`
  - 전제: `premise_refs`{`demand_input_id`, `demand_input_version`, `baseline_demand_version`, `inbound_schedule_version`, `ordering_rule_version`}
  - 기록: `judgment_due`, `source_type=계산`, `is_simulation`, `scenario_id`
- 판정 마감: `deadline_schedule.judgment_due`를 표시한다. 마감 경과 경고는 문제 4가 낸다.
- 다시 판정하는 때(조정자 D (2)):
  - 종결된 기안(`plan_status` ∈ {`확정`, `기한 경과 확정`, `철회`})은 판정을 동결한다. 어떤 사건에도 다시 판정하지 않는다.
  - 전제를 바꾸는 사건(`INBOUND_SCHEDULE_REVISED`(문제 2 자신이 낸 것도 구독), `BASELINE_DEMAND_SET`, `DEMAND_INPUT_REGISTERED`/`REVISED`, `PLAN_CONFIRMED`/`PLAN_AUTO_CONFIRMED_BY_DEADLINE`/`PLAN_WITHDRAWN`)를 받으면, 그 기안의 전제나 결론이 바뀐 경우에만 새 버전을 낸다(`caused_by` = 그 사건).
    - 기안의 전제 = 수요 입력 버전, 기준 수요 버전, 그 기안 SKU의 입고 행, 앞 순번 추가분이다. 수요 입력이 없는 기안은 앞 순번 추가분을 쓰지 않는다. 방향 판단도 기존 수요만으로 낸다.
    - 결론 = 판정값, 조건(종류·SKU·입고 행·발주안), 부족 주다.
    - 확인했지만 바뀌지 않은 기안은 `judgmentCheck`로 알 수 있다(9절).
    - 구독자는 p1→p4 순서로 불리므로 문제 4보다 먼저 판정한다. 문제 4는 이를 보고 `rejudge=false`로 재검토를 열고 닫는다.
  - 같은 날 승인된 발주안의 발주는 입고 버전 하나로 묶어 재판정을 한 번만 일으킨다.
  - `REVIEW_OPENED`(`target_type=supply_judgment`):
    - `rejudge=false`면 다시 계산하지 않는다. 같은 판정 버전을 또 만들지 않는다(조정자 확정 (5)).
    - `true`면 다시 계산해 새 버전을 `caused_by` = 그 사건으로 낸다. 내용이 같아도 낸다(유지 근거).
  - 전제에는 보충이 막힌 SKU 목록도 들어간다.
  - 원인과 사유(필수): 모든 판정 버전은 `caused_by`와 `generation_reason`을 가진다. 사유는 트리거 사건 종류와 바뀐 것(판정값, SKU별 판정·조건, 막을 수 없는 구간에 새로 들어온 부족 주, 거절로 막힌 SKU)을 적는다. 결론이 같으면 '결론 같음, 전제만 바뀜'. 날짜 경과는 발주 시한이 지난 조건 발주안의 `PO_DRAFT_CREATED`, 없으면 바뀌기 전 판정 사건을 원인으로 둔다. 수동 재판정도 앞 판정 사건을 원인으로 둔다.
  - 같은 날 묶기(조정자 F): 오늘 이미 이 기안의 판정 버전을 냈고, 새 계산의 결론과 SKU별 보충 필요량(`reorder_need.additional_reorder_qty_ea`)이 같으면 전제만 바뀐 것은 새 버전을 내지 않는다. 저장한 전제 키는 지금 것으로 바꾸고 `judgmentCheck`는 `changed=false`다. 그날 버전의 `premise_refs`는 그날 첫 전제를 가리킨다. 다음 날의 전제 변경은 규칙대로 새 버전을 낸다.
  - `onDay`: 날짜가 지나 막을 수 없는 구간이 밀린 경우에는 결론이 달라진 기안만 낸다. 이때 `generation_reason`은 '발주 시한 경과'다. 발주 시한이 지난 조건 발주안이 있으면 그 `PO_DRAFT_CREATED` 사건을 `caused_by`에 남긴다. 결론이 같으면 사건을 내지 않는다.
  - 유지/변경 종결은 문제 4가 한다.

### 4.5 대안 계산 `alternative`

`부족`·`조건부` 건과, 문제 3이 대안을 요청한 승인 거절 건에 계산하고 `ALTERNATIVES_COMPUTED`를 낸다. 시스템이 미리 좁히지 않는다.
- 시기이동의 권장 시작 주(`recommended_sale_start_week`)는 부족 SKU들의 `reorder_reach_week` 중 가장 늦은 주다(조정자 D (3)(다)). 그 시작이 실행 가능하지 않으면 가장 이른 실행 가능 주(`earliest_feasible_sale_start_week`)를 쓴다. `new_sale_start_week`는 권장 시작 주다.
- 시기이동·물량상한·구성이동·조기분할요청의 목표는 막을 수 없는 구간의 캠페인 부족을 0으로 만드는 것이다. 판정이 `부족`이면 `on_schedule`, 미확정 입고 조건부면 `not_arrived` 기준이다. `reorder_required`만 있으면 이 넷은 만들지 않는다.
- `보충발주`는 `부족` SKU와 `reorder_required` 조건 SKU에 만든다. 발주안이 거절돼 보충이 막힌 SKU에는 만들지 않는다. 선택하면 그 SKU의 열린 발주안에 이 기안을 잇는다(없으면 만든다).
- 보충이 막힌 SKU는 늦춰도 보충 가능 구간이 생기지 않으므로 시기이동 권장 시작 주 계산에서 뺀다. 평가 구간은 그 후보의 판매 기간 끝 주까지다.
- 권장 대안(`planAlternatives.recommended`, 부족·조건부일 때, v2.2 L4): 실행 가능한 시기이동·물량상한·구성이동마다 문제 1 미리보기로 같은 판정 규칙을 돌려 예상 판정을 내고 점수를 매긴다 — 가능 0, 조건부이면서 모든 조건이 확정기한 전에 풀릴 수 있으면 1(공급 확약 대기: 오늘 + 3영업일, 보충 발주 필요: 오늘 + 10영업일이 확정기한 안 / 미확정 입고: 그 기발주 회신 예정일이 확정기한 안), 풀릴 근거가 없는 조건(기준 수요 보충 미확인 등)이 있으면 2, 부족 3. 점수가 가장 낮고 지금 판정 점수보다 나은 것을 고르고, 같으면 계획을 덜 바꾸는 쪽(구성이동 < 물량상한 < 시기이동). 없으면 `null`(문제 4 기본 규칙상 철회). `recommended`에 `expected_verdict`, `score_label`, `resolvable_before_deadline`, `reason`, `compared[]`를 싣는다.

| `alternative_type` | 계산 값 | 실행 경로 |
|---|---|---|
| `시기이동` | `sale_weeks`를 유지한 채 `shortage_qty_campaign_ea` = 0이 되는 가장 이른 `new_sale_start_week` | 마케팅 선택 → `ALTERNATIVE_SELECTED`(`alternative_selection`) → 문제 1 새 버전. 계약상 이동 가능 여부는 마케팅 확인 |
| `물량상한` | 같은 기간에서 `shortage_qty_campaign_ea` = 0이 되는 최대 `new_uplift_pct` | 같음 |
| `구성이동` | 부족 SKU를 그 SKU의 물량상한으로 낮추고, 줄어든 EA를 같은 기안의 여지 있는 SKU에 `residual_headroom_qty` 한도 안에서 나눠 `new_override_uplift_pct[]`를 정한다. 다 배치하지 못한 EA는 표시한다 | 같음(C8). 라인을 넘는 대체는 마케팅 확인 |

- 후보 계산의 임시 추가 수량은 문제 1 `previewAddedQty`로만 계산한다(조정자 확정 (6)). 시기이동도 같은 함수로 새 시작 주의 EA를 받는다. 문제 1이 없거나 미리보기가 오류면 해당 대안은 `feasible=false`다. 선택되면 문제 1이 새 버전에서 정식으로 계산한다.
- `plan_change`(`plan_version`은 문제 2가 매김, 사전 A4): `settlement_date`, `requested_budget_krw`(마케팅 입력, 문제 2는 금액을 계산하지 않음), `change_reason`, `effective_at`. 경로 판정의 기안 총액은 원 기안 기준이다(U13, 문제 3).
- 비교 기준은 부족 수량과 부족 주수다. 품절 비용은 원본에 기록이 없어 금액으로 비교하지 않는다.
- 시연 대상이 아닌 기안은 대안을 계산해 보여주지만 선택 입력을 넣지 않는다(A3). "모의 입력 없음" 표시는 문제 4 `plan_state.mock_input_absent`다.

### 4.6 발주안 `po_draft`

발주안은 SKU 단위다(조정자 E (1)). 한 SKU에 열린(승인 전: `초안`·`승인대기`이고 승인 회신 전) 발주안은 하나다.
수량은 캠페인 추가분만 대상으로 한다(조정자 F (1), 범위: 캠페인 추가분의 공급 가능성과 승인 경로).

```
planned_order_date  = 그 SKU 발주안을 처음 만든 날 + 7영업일. 수량을 갱신해도 바꾸지 않는다     # K5
need_sum            = Σ 연결 기안의 uncovered_qty_ea                                        # 4.4
                      (= 캠페인 추가 필요량 − 승인 발주안 풀이 덮은 양. 추가 필요량은 기존 재고·미입고·승인 발주안 입고를 반영한 전개의 diff)
order_qty           = need_sum > 0 이면 max(올림(need_sum), moq), 아니면 발주안 없음              # U9
amount_krw          = order_qty × unit_cost_krw
expected_arrival_week = planned_order_date + lead_time_weeks 가 속한 주

수량 내역
order_qty_campaign_ea = need_sum           (qty_breakdown.campaign_added_ea)
rounding_ea           = order_qty − need_sum (MOQ·정수 올림분, 화면에 따로 표시)
order_qty_base_ea     = 0                  (기준 수요분은 넣지 않음)
campaign_share_pct    = need_sum ÷ order_qty × 100
qty_basis             = { campaign_need_ea, moq, moq_roundup_ea }
```

- 원본 산식 max(Target − 현재고 − 미입고, 0)은 발주안 수량에 쓰지 않고, 기준 수요 보충 필요량(4.8)을 계산하는 데 쓴다.
- `부족` SKU에 `보충발주` 대안을 고르면 그 SKU의 보충 가능 구간 캠페인 몫(`reorder_need.kind=shortage`)만큼 발주안에 넣는다. 그 몫이 0이면 대안은 `feasible=false`다(사유: 보충 가능 구간에 채워지지 않은 캠페인 추가 필요량 없음, 기준 수요 보충은 범위 밖).
- 연결 기안(`linked_plan_ids[]`): 그 SKU에 남은 보충 필요량이 있는 기안(순번 순)과 `보충발주` 대안으로 이은 기안이다. `qty_breakdown.campaign_by_plan[]`{`plan_id`, `qty_ea`, `needed_by_week`}에 기안별 몫을 남긴다.
- 갱신:
  - 등록 수요·입고가 바뀌어 승인 전 발주안의 `order_qty`가 바뀌면 같은 `po_draft_id`의 새 `draft_version`을 만들고 `PO_DRAFT_CREATED`(새 버전)를 낸다. 문제 3은 이를 받아 약정을 미상신으로 되돌리고 다시 판정한다.
  - 수량이 같고 연결 기안·내역만 바뀌면 버전을 올리지 않고 그 버전을 고친다(문제 3 약정의 상신 상태를 되돌리지 않기 위해).
  - 승인된 뒤 필요량이 늘면 승인 발주안은 그대로 두고, 승인 풀이 못 덮는 만큼만 새 초안(새 `po_draft_id`)을 만든다.
  - 연결 기안이 모두 빠지면(조건 해소·철회) 승인 전 발주안을 취소한다(`PO_DRAFT_CANCELLED`). 승인된 발주안은 취소하지 않는다.
- 판정이 바뀌지 않은 기안의 수요 변경도 수량에 반영되도록, 전제 변경 사건을 처리한 뒤 열린 발주안을 모두 다시 맞춘다.

- +7영업일의 근거:
  - 발주안의 승인 기준일은 `planned_order_date`다(C9).
  - 문제 4 산식으로 상신 마감 = 기준일 − 1 − (2 × `std_approval_bd` + 1)영업일, 판정 마감 = 상신 마감 − 1이다.
  - 경로는 지급일에 따라 정해지고 지급일은 발주일에 따라 정해지므로, 발주안을 만드는 시점에는 경로를 알 수 없다. 그래서 가장 긴 표준 결재(GRP_CEO 2영업일)로 잡아 판정 마감 = 선택일이 되게 했다.
  - 경로가 SCM으로 정해져도 날짜를 당기지 않는다(순환 재계산 방지).
- 필드(사전 3.2 `po_draft`): `po_draft_id`, `draft_version`, `sku_id`, `supplier_id`(Corevia), `order_qty`, `moq`, `planned_order_date`, `expected_arrival_week`, `unit_cost_krw`, `amount_krw`, `linked_plan_ids[]`, `qty_basis`{`target_qty`, `available_qty`, `undelivered_qty`, `suggested_qty`}, `arrives_before_gap`, `order_deadline`(연결 조건 중 가장 이른 발주 시한), `po_draft_status`(`초안` / `승인대기` / `발주` / `반려` / `취소`), `scenario_id`
  - (E)(F) 추가: `order_qty_base_ea`(F 이후 0), `order_qty_campaign_ea`(문제 3 명세가 정한 이름), `qty_breakdown`{`baseline_demand_ea`, `campaign_added_ea`, `rounding_ea`, `campaign_share_pct`, `campaign_amount_krw`, `campaign_by_plan[]`}. (F)에서 `qty_basis`는 {`campaign_need_ea`, `moq`, `moq_roundup_ea`}로 바뀌었다. 사전 등록 요청(8.2)
- `PO_DRAFT_CREATED`는 생성과 수량·날짜가 바뀌는 새 버전에만 낸다.
  - 상태 변경(`초안` → `승인대기` → `발주`/`반려`)은 사건을 다시 내지 않는다. 그 변경을 일으킨 사건(`PAYMENT_DATE_SET`, `APPROVAL_REPLIED`, 발주 시 `INBOUND_SCHEDULE_REVISED`)이 이력이 된다.
  - 이유: 문제 3이 `PO_DRAFT_CREATED`를 받으면 지급일을 다시 내고(`PAYMENT_DATE_SET`), 문제 2가 그것을 받으면 상태가 바뀌므로, 상태 변경마다 사건을 내면 끝없이 반복된다.
  - 수량이 0이 되어 취소되면 `PO_DRAFT_CANCELLED`를 낸다.
- `suggested_qty`는 소수(기준 수요가 소수 둘째 자리)일 수 있다. `order_qty`는 EA 정수로 올린 뒤 MOQ와 비교한다.
- 문제 3이 `payment_due_date`, `payment_rule_id`(월 마감 익월 21일, U11)와 경로를 정한다. 승인 회신(`APPROVAL_REPLIED`, 모의 자료는 문제 4)이 승인이면 발주(모의 전달)하고 `inbound_schedule`에 미회신 행을 추가해 전개를 다시 돈다.
- 미승인 상태로 `planned_order_date`가 지나면(U12 원칙):
  - 규칙을 만들지 않는다. 발주하지 않고 `승인대기`를 유지한다.
  - `INFO_REQUESTED`(`request_topic=po_draft_overdue`, `requested_to=SCM`)만 낸다. 경고는 문제 4가 낸다.
- `expected_arrival_week`가 `first_shortage_week`보다 늦으면 발주안은 만들되 `arrives_before_gap=false`다. 더마는 정상 리드타임 12주라 이 경우에 해당할 수 있다.

### 4.8 공급 확약·기준 수요 보충 (v2.0, 0절)

**입고 행 상태 `supply_status`**: `예상`(공급 확인 대기) → `확약`(Corevia·SCM 회신) → `입고 완료`(확약 행 도착일 경과, 조회 때 표시) / `미확약 잔량`(부분 공급의 남은 양) / `공급 불가`. 행 출처 `inbound_kind`: 기발주 / 운송 중 / 캠페인 발주안(`POD-`) / 정기 보충(`SCM-BR:`).
- 전개 두 경우: `on_schedule` = 예상·확약·입고 완료, `not_arrived` = 확약·입고 완료(예상 입고는 오지 않음). 미확약 잔량·공급 불가는 넣지 않는다.
- 승인된 발주안: 발주 예정일 + 리드타임의 `예상` 행. 발주 예정일에 상태만 `발주`. Corevia 회신으로만 `확약`.

**판정 조건(4.4에 더함)** — 확약 입고만 볼 때 캠페인 부족이 더 큰 주(예상 입고에 기대는 주)가 있으면, 그 주까지 도착하는 예상 행의 출처별로:
- `inbound_unconfirmed`(기발주·운송 중), `supply_commitment_pending`(공급 확약 대기: 승인된 캠페인 발주안), `baseline_replenishment_unconfirmed`(`reason=보충 계획 미확약`: SCM 확인·Corevia 미확약 보충 행). 필드 {`inbound_row_id`, `source_ref`, `eta_date`, `inbound_rows[]`{…, `qty`}, `relied_weeks[]`}.
- SCM 보충 계획이 확인되지 않은 SKU(미회신·SCM 미확인)는 판매 기간 뒤 부족을 `baseline_replenishment_unconfirmed`(`reason=보충 계획 미확인`, `after_sale_shortage_ea`, `first_week`)로 남긴다. 판매 기간 안은 종전대로 부족·보충 발주 필요로 가린다. 확인된 SKU는 판매 기간 뒤도 종전 규칙.

**Corevia 회신 반영** — `applySupplyCommitment`:
1. 같은 `record_id`·대상은 한 번만(재처리 무해). 더 낮은 버전은 받지 않는다. 정정은 새 버전이고 앞 버전은 남긴다.
2. 대상 입고 행의 처음 모습(`base_row`)에서 다시 만든다: 가능 → 확약(수량 = 요청, 날짜 = 회신, 늦으면 `eta_status=지연`), 부분 가능 → 확약 `committed_qty` 행 + `미확약 잔량` 행(`-R`), 불가 → `공급 불가`, 미확인·확인 필요 → `예상` 그대로.
3. 불가·부분 가능(정상)이면 그 발주안의 연결 기안·SKU 보충 발주를 막는다(`p2_reorder_block`, 4.4 거절과 같은 처리) → 남은 부족은 판매 기간 안 `부족` → 대안.
4. 사건: `SUPPLIER_REPLIED`(payload `supply_commitment`, `caused_by` = 발주안 승인 회신) → 입고가 바뀌면 `INBOUND_SCHEDULE_REVISED`(`caused_by` = 그 회신, payload `supply_commitment_id`) → 영향 기안 재판정(`SUPPLY_JUDGED`, 원인 = 입고 사건) → 대안 재계산(`ALTERNATIVES_COMPUTED`) → 문제 4 재검토.
5. 대안은 부족이거나 보충 발주 필요 외의 조건(미확정 입고·공급 확약 대기·기준 수요 보충 미확인)이 있으면 다시 계산한다.

**SCM 보충 계획 반영** — `applyBaselinePlan({ date | record_ids })`: SKU별 상태를 `p2_br_status`에 남기고 확인 행만 입고에 넣는다. `INBOUND_SCHEDULE_REVISED`(actor SCM, payload `baseline_replenishment[]`). 회신이 없으면 아무것도 바뀌지 않는다(자동 해소 없음).

**도착 시점(모의)**: S2-SCM-BR은 07-03, S2-CVC 기발주 대상은 `occurred_at`, 발주안 대상은 승인일 + `delay_bd_after_approval`영업일. 문제 2 `onDay`가 그날 도착분을 넣고, 문제 4 순서표가 `deliverMock`으로 먼저 넣어도 재처리 무해.
**같은 날 묶기(v2.1)**: 같은 날 도착한 Corevia 회신은 회신마다 `SUPPLIER_REPLIED`를 내고, 입고 일정은 새 버전 하나와 `INBOUND_SCHEDULE_REVISED` 하나(`caused_by` = 첫 회신, payload `supply_commitment_ids[]`·`supplier_replied_event_ids[]`)로 묶는다. Corevia 회신이나 SCM 보충 계획 회신이 바꾼 입고로 다시 판정할 때는 4.4의 같은 날 묶기를 적용하지 않는다(수요 입력이 있는 기안만). 공급 조건 변경이 재판정·재검토로 남게 하기 위해서다.

**입고 처리(v2.2 L7)** — `processArrivals(date)`(문제 2 `onDay`, 회신 반영 뒤): 확약 행의 `eta_date` ≤ 오늘이면 입고 실적(모의 입력, `received_qty` = 확약 수량, `receipt_is_synthetic=true`)으로 `입고 완료`. 예상 행의 원래 도착 예정일이 지났으면 `예정일 경과·미확약`(`original_eta_date`, `expected_now_week` = 다음 주 월요일, 주가 바뀔 때마다 갱신). 전개는 `on_schedule`에서 `expected_now_week`에, `not_arrived`에서는 빠진다 → 그 입고에 기대는 기안은 조건(미확정 입고·공급 확약 대기·기준 수요 보충 미확인)이나 부족으로 반영. 사건 `INBOUND_SCHEDULE_REVISED`(payload `receipts[]`, `overdue_expected[]`; 입고 실적이 있으면 `source_type=사람입력`, `is_synthetic=true`). 입고 완료는 판정 전제에서 확약과 같게 봐 새 판정 버전을 내지 않는다. 같은 날 다시 처리해도 바뀌지 않는다.

**공급 위험 수용(문제 4)**: 승인권자가 조건을 받아들인 승인 회신은 공급 상태를 바꾸지 않는다(문제 2는 승인 회신으로 입고 상태를 바꾸지 않음). 판정은 조건부로 남는다.

  - 사전에 있는 필드: `supply_request_id`, `supply_reply_type`(`조기` / `분할` / `추가`), `reply_result`(`가능` / `불가` / `조건부`), `offered_qty`, `offered_eta_date`, `required_checks`

## 5. 사건과 상태 전이

사건 이름과 payload 형식은 사전 5절, 공통 필드는 사전 3.4 `event`를 따른다.

### 5.1 문제 2가 받는 사건

| 사건 (내는 문제) | 문제 2의 처리 |
|---|---|
| `BASELINE_DEMAND_SET` (1) | 전개·여지 재계산, `SUPPLY_PROJECTED` |
| `DEMAND_INPUT_REGISTERED` / `DEMAND_INPUT_REVISED` (1) | 해당 기안 판정. 뒤 순번 기안은 `REVIEW_OPENED`로 받아 재판정 |
| `REVIEW_OPENED` (4, `target_type=supply_judgment`) | 다시 계산해 `SUPPLY_JUDGED` 새 버전 |
| `INFO_REPLIED` (4, 문제 2가 낸 요청의 회신 원문) | 4.1 구조화·확인 후 `INBOUND_SCHEDULE_REVISED` 또는 `SUPPLIER_REPLIED`로 등록 |
| `PAYMENT_DATE_SET`, `ROUTE_JUDGED` (3) | `po_draft_status=승인대기` |
| `APPROVAL_REPLIED` (4 모의 → 3 반영) | 발주안: 승인 → 입고 반영(`확정`)·발주 예정일에 `발주`. 거절 → `반려`, 연결 기안·SKU 보충 막힘, 그 기안 재판정(부족) → 대안 재계산. 기안 거절 → 문제 3 요청에 따라 대안 계산 |

### 5.3 상태 전이

**공급 판정** (기안 단위, 버전마다 불변)

```
(없음) ──SUPPLY_PROJECTED──▶ 판정불가(+direction_note)
판정불가 ──DEMAND_INPUT_REGISTERED──▶ 가능 | 조건부 | 부족
조건부 ──INBOUND_SCHEDULE_REVISED(확정·지연)──▶ 가능 | 부족
조건부/부족 ──ALTERNATIVE_SELECTED → DEMAND_INPUT_REVISED 또는 발주 승인·입고 반영──▶ 재판정
어느 상태든 ──REVIEW_OPENED──▶ 재판정 → 문제 4 REVIEW_CLOSED(유지/변경)
```

**발주안** (`po_draft_status`)

```
초안 ──PAYMENT_DATE_SET·ROUTE_JUDGED──▶ 승인대기 ──APPROVAL_REPLIED 승인──▶ 발주 ──▶ INBOUND_SCHEDULE_REVISED(미회신 행)
                                              ├─ 거절 ──▶ 반려 ──▶ 연결 기안 SKU 보충 막힘 → 재판정(부족) → 대안 재계산
                                              └─ 조건부 ──▶ 조건 반영 새 버전 또는 반려
승인대기 ──planned_order_date 경과(미승인)──▶ 승인대기 유지 + INFO_REQUESTED(po_draft_overdue) (규칙 없음, U12)
초안/승인대기 ──등록 수요 변경으로 수량 변경──▶ 같은 상태, 새 draft_version(PO_DRAFT_CREATED)
초안/승인대기 ──연결 기안이 모두 빠짐──▶ 취소(PO_DRAFT_CANCELLED)
```

**공급 요청** (`supply_request_status`): `요청 → 회신됨(SUPPLIER_REPLIED) → 반영 | 제외`

**입고 일정 행**: `미회신 → 확정 | 지연`(새 버전). 재지연도 새 버전이다.

## 9. 모듈 공개 함수(expose)

다른 모듈은 `ctx.module('p2')?.<함수>(...)`로 부른다. 연결 전이면 `null`이다.
- 모든 함수는 현재 DB 상태를 읽어 돌려주며 다시 계산하지 않는다. 동기 함수다.
- 단, 9.2의 입력 함수는 사건을 내므로 `async`다.
- 반환 객체의 필드 이름은 사전(`problem4/공통_접점.md`) 3.2절을 따른다. 목록 필드는 배열, 묶음 필드(`premise_refs`, `qty_basis`, `condition_basis[]`)는 객체다.
- 찾는 값이 없으면 `null`(단건) 또는 `[]`(목록)을 돌려준다.

| 화면 API | `planDecision`에 `waiting_replies[]`{`from`, `what`, `status`, `expected_by`}, `next_actions[]`, `conditions[].condition_type`/`waiting_on`, `background.baseline_plan[]` 추가 |

### 9.3 구독할 사건

`BASELINE_DEMAND_SET`, `INBOUND_SCHEDULE_REVISED`(자기 사건), `DEMAND_INPUT_REGISTERED`, `DEMAND_INPUT_REVISED`, `REVIEW_OPENED`, `INFO_REPLIED`, `AI_OUTPUT_REVIEWED`, `PAYMENT_DATE_SET`, `ROUTE_JUDGED`, `APPROVAL_REPLIED`, `CASH_WINDOW_REVISED`, `PLAN_CONFIRMED`, `PLAN_AUTO_CONFIRMED_BY_DEADLINE`, `PLAN_WITHDRAWN`

추가로 `ctx.clock.onDay`에서 두 가지를 처리한다.
- 승인된 발주안은 `planned_order_date`에 발주한다.
- 미승인 발주안이 `planned_order_date`를 지나면 `INFO_REQUESTED`(`po_draft_overdue`)를 낸다.
