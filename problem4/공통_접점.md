## 0. 이름을 정한 순서

1. **조정자 확정 (2026-11-15)** 을 먼저 적용한다.
   - K1: 추가 수량 `added_qty_ea`는 문제 1이 계산해 `campaign_demand_weekly`로 넘기고 문제 2는 다시 계산하지 않는다. `uplift_pct`는 % 단위다. `added_qty_ea = round(baseline_weekly_qty × applied_uplift_pct ÷ 100)`이고, SKU별 `override_uplift_pct`가 있으면 그 값을 쓴다.
   - K2: 발주안 식별자는 `po_draft_id`, 사건은 `PO_DRAFT_CREATED`다.
   - K3: 공급 판정은 어디서나 `supply_judgment_id`, `supply_verdict`, `supply_judgment_version`이다.
   - K4: 현금 구간은 `window_version`, `shortfall_window_start`, `shortfall_window_end`를 펼친 필드로 쓴다.
   - K5: `planned_order_date`는 대안 선택일 + 7영업일이다(문제 2 규칙).
   - K6: 모의 입력의 도착일은 문제 4 사건 순서표를 따른다.
   - K7: 그룹 300억 배분 확인 요청은 문제 4만 낸다.
   - K8: 잔여 여지는 입고 경우 두 가지(전체 반영 `on_schedule` / 확정 입고만 반영 `not_arrived`)로 넘긴다.
   - K9: 사건 이름은 대문자 스네이크이고 최종 이름은 이 파일 5절이 정한다.
2. 나머지는 **소유 문제 최신 명세(v0.2)의 이름**을 따른다.
3. 소유자끼리도 엇갈리거나 정의가 비어 있으면 문제 4가 하나로 정했다. 이 항목 A1~A6은 2026-11-15 조정자가 확정했다(6절).

## 2. 공통 규칙

| 항목 | 규칙 |
|---|---|
| 필드 이름 | 소문자 스네이크. 목록은 이름 뒤에 `[]`, 묶음은 `{}` |
| 사건 이름 | 대문자 스네이크(K9) |
| 날짜 | `YYYY-MM-DD`. 가상 일자다. 실제 시각은 `recorded_at`에만 쓴다 |
| 주 | `week_start` = 그 주 월요일 날짜. 주 격자는 문제 2 소유이며, 첫 전개 주는 2026-07-06, `projection_end_week` = 2026-12-28 |
| 영업일 | 월~금, 공휴일 없음 [원본: A05 §2]. 일수 필드 이름은 `_bd`로 끝난다 |
| 금액 | 원(KRW, VAT 제외) 정수, 이름은 `_krw`로 끝난다. 기안 금액은 표본 스케일이므로 현금과 합산하지 않는다 |
| 수량 | EA 정수, 이름은 `_qty` 또는 `_ea`로 끝난다 |
| 비율 | `_pct`는 % 숫자다(35.0 = 35%) |
| 해당 없음 | 코드 `NONE`. 0과 다르다 [원본: data_dictionary] |
| 버전 참조 | 객체 안의 버전 필드는 그 객체 정의를 따르고, 다른 객체가 참조할 때는 `<객체>_version`으로 쓴다. 예: `demand_input.version` → 참조 시 `demand_input_version` [A3 확정] |
| 열거값 | 아래 표에 적힌 글자 그대로 저장한다(띄어쓰기 포함) |
| 저장 | 원본 CSV는 읽기 전용. 합성 속성은 각 문제 폴더 아래 별도 폴더의 파이프(`|`) 구분 CSV. 실행 중 사건·판정·상태는 SQLite 파일 [사용자 결정 2026-11-15] |

**`po_draft`** — 받는 문제: 3, 4 / 키: (`po_draft_id`, `draft_version`) / 정의: `problem2/명세.md` 4.6절

- SKU 단위 규칙 [조정자 확정 (E)-1, (F)-1]:
  - 발주안은 기안 단위가 아니라 SKU 단위다. 한 SKU에 열린(승인 회신 전) 발주안은 하나다.
  - 수량은 그 SKU에 걸린 캠페인 추가분(철회되지 않은 기안의 유효한 캠페인 추가분) 가운데 기존 재고·미입고·승인된 발주안으로 채워지지 않는 양(`qty_basis.campaign_need_ea`)만이다. MOQ보다 작으면 MOQ로 올리고 올림분을 표시한다(`qty_basis.moq_roundup_ea`, `qty_breakdown.rounding_ea`). [(F)-1]
  - 기준 수요의 보충 필요량은 발주안에 넣지 않는다. 범위 밖(SCM 정기 발주 소관) 배경 제약으로 `baseline_replenishment`에 따로 계산·표시하고 SCM 확인 요청으로 넘긴다. 원본 산식 `max(Target Qty − 현재고 − 미입고 물량, 0)`은 이 배경 수치에만 쓴다. [(F)-1]
  - 기안의 보충 조건(`condition_basis[].reorder_required.po_draft_id`)은 그 SKU의 발주안을 가리킨다.
  - 이미 승인된 발주안이 필요량을 덮으면 새로 만들지 않고 조건 충족으로 본다(`covered_by_approved_qty_ea`).
  - 등록 수요가 늘어 수량이 모자라면, 승인 전 초안은 같은 `po_draft_id`의 새 `draft_version`으로 수량을 갱신하고(`PO_DRAFT_CREATED`), 승인된 뒤라면 추가분만 새 초안(새 `po_draft_id`)으로 만든다.
  - 기안 철회에 따른 처리 구분 [v1.15, 문제 2 v2.3]: `withdrawal`{`plan_id`, `withdrawn_event_id`, `disposition`}. `disposition` = `취소`(`PO_DRAFT_CANCELLED`, `linked_plan_ids`=[]·`linked_plan_ids_before`) / `기안만 뗌` / `기안만 뗌(수량 재계산, 다시 승인)`(새 `draft_version`의 `PO_DRAFT_CREATED`) / `발주 전달 뒤 남음`(`orphan_status`, SCM 확인 요청 `po_draft_orphaned`) / `기안만 뗌(발주 전달 뒤)`. 수량·판이 그대로인 연결 기안 변경은 같은 `draft_version`의 `PO_DRAFT_CREATED`(`change_kind='linked_plans_changed'`, `linked_plan_ids`, `linked_plan_ids_before`)로 알린다. 받는 쪽은 이 판을 새 발주안으로 보지 않는다(승인 상태 유지, 마감 재산출 없음). 연결 기안의 기준은 문제 2 `linked_plan_ids`다.
  - 연결 기안이 모두 빠지면 승인 전 발주안은 취소한다(`PO_DRAFT_CANCELLED`). 승인된 발주안은 기안 철회 때 [조정자 확정 L1, v1.14]: 발주 전달 전(오늘 < `planned_order_date`)이고 그 기안에만 걸렸으면 취소(`cancel_reason`='연결 기안 철회(발주 전달 전, 승인 발주안 취소)', 예상 입고 삭제, 문제 3이 약정·유출을 뺌). 다른 기안도 걸렸으면 그 기안만 떼고 수량을 다시 계산(새 `draft_version`, 다시 승인). 발주가 이미 전달됐으면 취소하지 않고 `orphan_status='기안 철회 뒤 남은 발주'`, SCM에 `INFO_REQUESTED`(`po_draft_orphaned`). 이전 규칙(승인된 발주안은 취소하지 않음)을 이렇게 바꿨다. 문제 4는 취소된 발주안의 마감 행을 `computed_status=취소(발주안 취소)`로 두고 상신·경고를 내지 않는다.

## 8. AI 호출 설정 [사용자 결정 2026-11-15]

모델은 작업 종류별로 고정한다. 가격은 고려하지 않고 품질 기준으로 정했다.

### 8.1 호출 경로

| 항목 | 값 |
|---|---|
| API | OpenRouter chat completions API |
| 키 | 환경 변수 `OPENROUTER_API_KEY`. 키는 저장소(코드·CSV·SQLite·로그)에 두지 않는다 |
| 키가 없을 때 | 'AI 미연결' 상태로 동작한다. 해당 구간(구조화·작성)은 사람이 직접 입력한다. 계산·판정·상태 전이는 AI와 무관하게 그대로 작동한다 |
| 모델 자동 선택 | `openrouter/auto`는 쓰지 않는다. 요청마다 모델이 달라져 재현이 안 된다 |

### 8.2 작업 종류와 모델

| `ai_task_type` | 대상 작업 | 모델(기본값) | 바꾸는 환경 변수 |
|---|---|---|---|
| `structure` | 자유 서술을 구조화된 입력으로 변환. 예: 마케팅 수요 회신, 공급자 납기 회신, 조건부 승인 문장 | `anthropic/claude-opus-5.5` | `AI_MODEL_STRUCTURE` |
| `write` | 판정 변경 이유 설명, 대안별 차이 설명, 상신 문서 초안, 새 사건의 영향 요약 | `anthropic/claude-fable-5.2` | `AI_MODEL_WRITE` |

### 8.3 작업별 규칙

- `structure`
  - 회신에 없는 값은 추측하지 않는다. 그 필드는 `null`로 두고 `unclear_reasons[]`에 불명확 사유를 적는다.
  - 결과는 담당자가 확인(`AI_OUTPUT_REVIEWED`)한 뒤에만 반영된다. 확인 전 결과는 판정·상태에 쓰이지 않는다.
  - 예: 문제 1 `DEMAND_INPUT_STRUCTURED`는 확인 전 구조화 결과이고, `DEMAND_INPUT_REGISTERED`·`REVISED`는 확인 뒤에 나온다.
- `write`
  - 수치·날짜·판정은 시스템이 계산한 값만 인용한다. 입력으로 받은 값 밖의 수치를 만들지 않는다.
  - AI가 계산하거나 판정하지 않는다. 판정·마감·경로·재검토 대상 선택은 규칙이 한다.
  - 문서 초안은 담당자가 확인한 뒤에 쓰인다(상신 문서는 사람이 상신).
- 공통: AI는 사건을 직접 만들거나 상태를 바꾸지 않는다. AI 출력은 `AI_CALL_RECORDED`로만 남고, 반영은 사람 확인을 거친 소유 문제의 사건으로 일어난다.

- 공개 함수 `isDirectPlan(plan_id)` → boolean [v1.15]. `listDirectPlans()`는 부를 때마다 지금 값(복사본). 모의 입력을 스스로 넣는 모듈은 직접 처리 기안을 빼야 한다: 문제 3 자동 묶음 상신(`deliverMock`, `POST /api/p3/submit`)은 직접 처리 기안을 묶음에서 빼고 그 기안의 순서표 상신 행은 건너뛴다(`skipped`). 사용자가 고르는 `bundle_candidates`에는 남는다 [v1.15].
- 직접 처리 기안이 기한 경과로 끝나면 `PLAN_AUTO_CONFIRMED_BY_DEADLINE.payload.direct_no_input`{`direct`, `awaited[]`(수요 입력·대안 선택 또는 철회·승인 요청 올리기·확정), `note`}를 남기고 경위에 '담당자 입력 없음'을 적는다 [v1.14 L8].
- 건너뛰는 모의 입력: 수요 회신(정시·늦은·정정), 대안 선택(마케팅), 조기 공급 요청, 권장 대안 선택, 기본 모의 입력의 시기 이동·철회, 확정, 기안 약정 상신. 계속 오는 모의 입력: 승인 회신·조건 수용(승인권자), 발주안 상신(SCM), 입고·재무·Corevia·그룹 회신.

## 10. 공급 확약·원료·생산 제약 [사용자 요청 2026-11-15]

- 내부 발주 승인(구매·지출 허용) ≠ Corevia 공급 확약(수량·납기 약속) ≠ 입고 완료. 승인된 발주안은 `예상` 입고로만 들어가고, Corevia 확약 회신으로만 `확약`이 된다(3.2 `inbound_schedule.supply_status`).
- 공급 판정: 확약 입고만으로 성립하면 `가능`, 예상 입고나 미확인 조건에 기대야 하면 `조건부`(`inbound_unconfirmed` / `supply_commitment_pending` / `baseline_replenishment_unconfirmed`).
- 재검토 대응(문제 4): `SUPPLIER_REPLIED`(공급 확약 회신·정정: 확약, 부분 가능, 지연, 불가, 미확인, 확인 필요)와 `INBOUND_SCHEDULE_REVISED`(회신 반영·SCM 보충 계획) → 그 SKU와 `linked_plan_ids`의 공급 판정 재검토를 연다. 문제 2가 회신 사건을 원인으로 다시 판정하면 직전 결론과 비교해 닫고, 결론이 `부족`이면 대안 선택(직접 처리: 담당자, 자동: 기본 모의 입력)으로 잇는다. SCM 회신이 온 SKU의 `baseline_replenishment` 확인 요청을 닫는다.
- 확정 가능(문제 4 4.5): 공급 미확약 조건이 남으면 승인돼도 `조건부 대기`. 승인권자의 공급 위험 수용 회신(`APPROVAL_REPLIED.payload.supply_risk_accepted=true`, `accepted_condition_types[]`, 조건 `acceptance_type=공급 위험 수용`)이 남은 조건을 모두 덮으면 `위험 수용 확정 가능`. 그 상태로 확정하면 `decision_snapshot.confirmed_under_risk=true`, `supply_note=공급 미확약 상태로 확정(위험 수용)`이 남는다. 공급 판정·입고 상태는 바꾸지 않는다. 문제 3은 이를 `commitment.supply_risk_acceptance`{`accepted`, `accepted_condition_types[]`, `approver`, `approval_request_id`, `replied_at`, `event_id`, `note`}로 남긴다.
- 모의 입력(문제 4 사건 순서표): Corevia 공급 회신은 발주안 내부 승인 뒤 문제 2 자료의 도착일에 `deliverMock`으로(M20), SCM 기준 수요 보충 계획은 07-03에(M19) 도착한다. 공급 위험 수용은 지정 사례(S4-08 `round=RISK`: PLAN-011. v1.15에서 PLAN-021·019를 바꿈. S-CEO-FLOOR에서는 시나리오 전용 행 S4-08-12 `decision=미수용`이 앞서 위험 수용 회신이 없고 기본 규칙대로 철회 [v1.16])에서만 확정기한 2영업일 전까지 조건이 남으면 넣는다(M18). 그 밖의 자동 처리 기안은 회신이 없어 조건이 남으면 확정기한 2영업일 전 권장 대안, 전 영업일 철회로 이어진다.
- 현금: 발주안 지급 유출은 내부 승인 때 한 번(같은 회신 재처리로 늘지 않음). 부분 공급 때 지급 금액은 근거가 없어 발주 금액 그대로(한계). 공급 불가(검증 정상)면 문제 3이 그 발주안 약정을 `취소`로 두고 유출을 뺀다. SCM 정기 발주의 유출은 재전망에 없다(한계).
