- 조건 4가 왜 생겼는지(어느 부서가 늦었는지, 기록이 실제 조직에 있는지)는 원본으로 가릴 수 없다. 이 명세는 원인을 단정하지 않는다. 실행 중에 생기는 요청·회신·결정을 기록하고, 그 위에서 재검토·보류·기한을 관리하는 장치만 정의한다.
- 마스터 자료(SKU·공급처·승인권자·기안)의 합성 속성은 맡지 않는다 [사용자 결정 U9].

### 1.2 받는 것과 넘기는 것

필드 목록은 `problem4/공통_접점.md` 3절의 객체 정의를 그대로 쓴다. 여기서는 어떤 객체를 주고받는지만 적는다.

| 상대 | 받는 객체 | 넘기는 객체 |
|---|---|---|
| 문제 1 | `plan_sku_map`(같은 SKU 기안 찾기), `demand_input`, `demand_status_by_plan`, `baseline_demand`·`campaign_demand_weekly`의 버전 | `deadline_schedule.demand_input_due`, `info_request`(`request_topic=demand_input`), `review`(`target_type=info_request` / `demand_input`), `hold`, `plan_state` |
| 문제 2 | `supply_judgment`, `inbound_schedule`, `alternative`·`alternative_selection`·`plan_change`, `po_draft`, `supply_request` | `deadline_schedule.judgment_due`, `review`(`target_type=supply_judgment`), `plan_state`(누적 순서의 "확정된 건" = `plan_status` ∈ {`확정`, `기한 경과 확정`}, `철회`는 제외), `info_request`(`inbound_eta` / `supply_request` / `po_draft_overdue`) |
| 문제 3 | `commitment`(`approval_status`, `approval_anchor_date`, `anchor_basis`, `approver`), `route_judgment`, `cash_window`, `approver_role.std_approval_bd`, `approval_request` | `deadline_schedule` 전체, `approval_reply`(`APPROVAL_REPLIED`), `review`(`target_type=route_judgment` / `commitment`), `plan_state`, `PLAN_AUTO_CONFIRMED_BY_DEADLINE`, `open_issue`, `info_request`(`group_report` / `finance_confirmation` / `settlement_unapproved` / `source_unknown`) |

- 추가 수량 EA는 문제 1의 `campaign_demand_weekly.added_qty_ea`다. 문제 4는 값을 다시 계산하지 않고 버전만 전제로 연결한다 [조정자 확정 K1].
- 같은 SKU 기안의 순서는 문제 2 규칙(확정된 건 → `contract_deadline` → `settlement_date` → `plan_id`)을 따른다. "확정된 건"은 `plan_status` ∈ {`확정`, `기한 경과 확정`}이고 `철회`는 순서에서 뺀다 [사전 v1.1].
- 공급 판정 가능 여부는 `demand_status`가 아니라 `version_status=유효`인 수요 입력 버전이 있는지로 본다. 정정 확인 중에도 이전 유효 버전이 살아 있어 기존 판정이 `판정불가`로 떨어지지 않는다 [사전 v1.1].
- 그룹 300억 배분 확인 요청은 문제 4만 낸다 [조정자 확정 K7].

### 1.3 구현 형태 [사용자 결정, 2026-11-15]

- 기존 Node 22 서버(`server.mjs`, Docker·axhub 배포)를 유지한다.
- 실행 중 사건(`event`)·판정·상태는 SQLite 파일에 저장한다. 사건 행은 지우거나 고치지 않고 쌓기만 한다.
- 문제 4의 합성 속성·운영 가정(S4-01~S4-09)은 `problem4/` 아래 별도 폴더의 파이프(`|`) 구분 CSV로 둔다(파일은 아직 만들지 않음). 원본 CSV는 읽기 전용이다.
- 운영 중 AI 호출 설정은 `problem4/공통_접점.md` 8절을 따른다 [사용자 결정 2026-11-15].
  - 경로: OpenRouter chat completions API, 키는 환경 변수 `OPENROUTER_API_KEY`이며 저장소에 두지 않는다. `openrouter/auto`는 쓰지 않는다.
  - 문제 4가 AI를 쓰는 일은 작성 작업(`ai_task_type=write`) 하나다: 새 사건이 어느 기안에 영향을 주는지 담당자가 읽을 요약(`event_impact_summary`). 모델은 `anthropic/claude-fable-5.2`(`AI_MODEL_WRITE`로 변경 가능)이다.
  - 요약은 재검토 대응표(4.4)가 고른 대상과 시스템이 계산한 값만 인용한다. AI는 재검토 대상 선택, 마감 계산, 판정, 상태 전이를 하지 않는다.
  - 경고 문구(S4-02)는 AI 초안 없이 규칙의 고정 문구를 쓴다.
  - 호출마다 `AI_CALL_RECORDED`(모델 이름, 작업 종류, 입력 참조, 출력, 확인 여부)를 남기고, 담당자 확인은 `AI_OUTPUT_REVIEWED`로 남긴다.
- 키가 없으면 'AI 미연결' 상태로 동작한다. 요약 대신 규칙이 만든 영향 기안 목록만 보여주고, 필요한 설명은 담당자가 직접 입력한다.

## 4. 판정·처리 규칙

### 4.1 `is_simulation` 판정 [조정자 기준 C8]

- 입력: 사건의 `source_type`, `is_synthetic`, `premise_refs`가 가리키는 사건·버전.
- 계산:
  - 사건 자체가 `source_type ∈ {사람입력, 모의회신, 가정}`이거나 `is_synthetic = true`이면 `is_simulation = true`다.
  - 그 밖에는 `premise_refs` 중 하나라도 위 조건이거나 `is_simulation = true`이면 true, 아니면 false다. 전제를 따라 끝까지 이어 붙인다.
- 결과 예:
  - false로 남는 것: 원본만으로 낸 계산. 예를 들어 문제 3의 기본 재계산 구간과 그 구간으로 낸 기안 경로 판정.
  - true가 되는 것: `added_qty_ea`와 그것을 쓴 공급 판정, 합성 결제 조건으로 낸 `payment_due_date`.
- 시연 단계의 사람 입력은 모두 가상이므로 `사람입력` 사건은 `is_synthetic = true`다.

### 4.2 마감 산식 `deadline_schedule` [문제 4 소유]

- 입력: `commitment.approval_anchor_date`, `anchor_basis`, `approver`, `approver_role.std_approval_bd`(U11), S4-01 일수.
- 계산(영업일):
  - `final_reply_due` = 기준일 − 1
  - `submission_due` = `final_reply_due` − (2 × `std_approval_bd` + 1). 1차 결재, 대안 선택 1일, 재상신 결재를 포함한다.
  - `judgment_due` = `submission_due` − 1
  - `demand_input_due` = `submission_due` − 2 (기안만)
  - `first_reply_due` = `submission_due` + `std_approval_bd`, `alt_selection_due` = `first_reply_due` + 1
- 예 [계산]: 기준일 07-17(금), `std_approval_bd = 2` → 수요 입력 07-07, 판정·재무 확인 07-08, 상신 07-09, 1차 회신 07-13, 대안 선택 07-14, 최종 회신 07-16. 기안 전체는 3.2 표.
- 결과: `deadline_schedule`과 `DEADLINES_SET`. 승인권자나 기준일이 바뀌면 `DEADLINES_RECOMPUTED`(이전 값 포함)를 낸다. 거절·철회로는 다시 산출하지 않는다(U15).

### 4.3 확인 요청 `info_request`

- 발행: 모든 문제의 확인 요청은 `INFO_REQUESTED`로 낸다. 요청 항목과 대상 부서는 요청하는 문제가 정하고, 문제 4는 `request_id`·`request_due_date`·`request_status`를 관리한다.

  | `request_topic` | 요청하는 문제 | `request_due_date` |
  |---|---|---|
  | `demand_input` | 1 | `demand_input_due` |
  | `inbound_eta`, `supply_request`, `po_draft_overdue` | 2 | 요청하는 문제가 정함(판정 마감 이전) |
  | `finance_confirmation` | 3 | `judgment_due` |
  | `group_report` | 3(R9) | 승인 반영 다음 영업일 [가정] |
  | `group_allocation` | 4(OI-3) | 07-08 |
  | `settlement_unapproved` | 4(W6) | 기준일 다음 영업일 [가정] |
  | `source_unknown` | 1·2·3의 7절 확인 불가 항목 | 요청하는 문제가 정함 |

- 처리: 회신(`INFO_REPLIED` 또는 소유 문제의 회신 사건)이 `caused_by`로 요청을 가리키면 `회신됨`이 된다. 기한이 지나면 `기한 경과`가 되고 W1·W7과 `review`(`review_kind=기한 경과 후속`)를 낸다. 재요청(`request_kind=rerequest`)은 문제 4가 `INFO_REQUESTED`로 내고 이전 요청은 `이관`이 된다. 보류를 걸면 `보류`가 된다. 늦은 회신도 `회신됨`(지연 표시)으로 받는다.
- 반려 뒤 재요청: 문제 1의 `DEMAND_INPUT_REJECTED`를 받으면 문제 4가 `INFO_REQUESTED`(`request_topic=demand_input`, `request_kind=rerequest`, `caused_by`=반려 사건, `request_due_date`=원래 `demand_input_due`)를 낸다. 원래 마감이 이미 지났으면 다음 영업일로 둔다 [가정]. 이전 유효 버전이 있으면 판정은 그 버전으로 계속된다 [사전 v1.1].
- 소요 시간(R6): `회신.occurred_at − 요청.occurred_at`(영업일). 요청이나 회신 중 하나라도 `is_synthetic`이면 '모의 결과'로 표시한다.

### 4.4 재검토 `review` [R2, S4-04]

| 트리거 사건 | 열리는 대상 (`target_type`) |
|---|---|
| `DEMAND_INPUT_REGISTERED` / `DEMAND_INPUT_REVISED` (기안 P) | P의 `supply_judgment`, 같은 SKU를 쓰고 판매 기간이 겹치며 순서상 P보다 뒤인 기안의 `supply_judgment` |
| `BASELINE_DEMAND_SET` (버전 변경) | 그 버전을 쓴 모든 `supply_judgment`(시연에서는 발생하지 않을 것으로 예상) |
| `INBOUND_SCHEDULE_REVISED` / 수량·일자를 바꾸는 `SUPPLIER_REPLIED` | 해당 SKU를 쓰는 모든 `supply_judgment` |
| `PLAN_CONFIRMED` / `PLAN_AUTO_CONFIRMED_BY_DEADLINE` / `PLAN_WITHDRAWN` (기안 P) | 같은 SKU에서 P보다 뒤 순서인 기안의 `supply_judgment`. 앞의 둘은 P를 "확정된 건"으로 올리고, 철회는 P를 순서에서 뺀다 |
| `ALTERNATIVE_SELECTED` (기안 P) | 같은 SKU 뒤 순서 기안의 `supply_judgment`. `plan_change`가 있으면 P의 `route_judgment` |
| `PO_DRAFT_CREATED` / `PAYMENT_DATE_SET` | 그 발주안의 `route_judgment` |
| `CASH_WINDOW_REVISED` (구간이 바뀐 경우) | 유출일이 이전 또는 새 구간에 드는 약정의 `route_judgment`, 그 약정 중 `결재 대기`·`승인`인 `commitment` |
| `ROUTE_JUDGED`에서 `approver`가 바뀜 | `DEADLINES_RECOMPUTED`, 그 `commitment` |
| `APPROVAL_REPLIED`의 `conditions[]`에 `기타`가 있음 | 그 `commitment`(`review_kind=사람 판단`, 유지로 닫으면 조건 충족 확인) |
| `INFO_REPLIED` (OI-3 `대상`) | `plan_bundle` 1건(`review_kind=사람 판단`) |
| `DEADLINE_WARNED` W1 | 해당 `info_request`(`review_kind=기한 경과 후속`). 재요청은 문제 4가 낸다(4.3) |
| `DEADLINE_WARNED` W7 | 해당 `info_request`(`review_kind=기한 경과 후속`) |

종결 규칙:

- `supply_judgment`: `supply_verdict`와 (부족이면) `first_shortage_week`가 같으면 `유지`, 다르면 `변경`. 수량 변화는 `before`/`after`에 남긴다. 소유 문제가 새 `supply_judgment_version`을 `caused_by = REVIEW_OPENED`로 내면 문제 4가 비교해 닫는다.
- `route_judgment`: `approver`와 `submission_due`가 같으면 `유지`(문제 3 `route_changed=false`).
- `commitment`(결재 대기·승인 건): 자동으로 바꾸지 않는다. 경로가 바뀌었거나 금액·유출일이 바뀌었으면 재상신으로 넘긴다. 문제 3 4.8 표(경로 상향·하향별 처리)를 따르고, 기존 승인 사건은 지우지 않는다.
- 모든 종결에 `rationale`을 남긴다. `유지`도 근거 없이 닫지 않는다.

### 4.5 기안 확정 가능 상태 `plan_state.plan_confirmability` [C7·C17, S4-05]

- 입력:
  - 최신 `supply_judgment`(기안 행)의 `supply_verdict`와 `condition_basis[]`
  - `commitment.approval_status`(`미상신` / `결재 대기` / `승인` / `조건부` / `거절`)
  - 최신 `APPROVAL_REPLIED.conditions[]`
  - 열린 `review`·`hold`
  - `plan_status`
- 계산(위에서부터 처음 맞는 규칙):
  1. `plan_status` ∈ {`확정`, `철회`, `기한 경과 확정`}이면 그 상태로 종결.
  2. 열린 `review` 또는 `hold`가 있으면 `미확인`.
  3. `supply_verdict = 판정불가`(유효 수요 입력 버전 없음), 또는 `approval_status` ∈ {`미상신`, `결재 대기`}이면 `미확인`. 정정 확인 중(`demand_status=확인대기`)이어도 유효 버전이 있으면 이 규칙에 걸리지 않는다.
  4. `supply_verdict = 부족` 또는 `approval_status = 거절`이면 `불가`(대안 선택 대기).
  5. `supply_verdict = 조건부`일 때:
     - 최신 회신의 `conditions[]`에 `condition_type = 공급조건부수용`이고 `ref_id`가 그 `supply_judgment_id`인 항목이 있으면 6으로 간다.
     - 없으면 `조건부 대기`.
     - 판정 버전이 바뀌면 수용은 다시 받아야 한다.
  6. `approval_status = 조건부`이면 조건별로 충족을 확인한다. 하나라도 미충족이면 `조건부 대기`다.
     - `수요·공급 확인 후`: 최신 `supply_verdict = 가능`이면 충족.
     - `기타`: 4.4의 사람 판단 `review`가 유지로 닫히면 충족.
  7. `approval_status = 승인`(또는 6을 통과한 `조건부`)이면 `확정 가능`.
- 표시만 하고 상태를 바꾸지 않는 것(U4, P1, R9):
  - `stock_warning`, `safety_breach_weeks`, `preventable_by_reorder`
  - 그룹 보고 요청
- 결과: 상태가 바뀌면 `PLAN_CONFIRMABILITY_CHANGED`를 낸다. 실제 확정은 마케팅의 `PLAN_CONFIRMED`(사람입력)로만 일어나며 `확정 가능`일 때만 받는다. 시스템은 확정하지 않는다.

### 9.5 구현 메모 (B1, 2026-11-15)

- 모의 입력 전달: 값의 소유 모듈이 `deliverMock(mock_id)`를 내놓았으면 그것을 부르고, 없으면 문제 4가 같은 사건을 직접 낸다. 정시 수요 회신(M02)은 문제 1 자료에 `on_time` 행이 있는 기안만 순서표에 올린다.
- 순서표 행의 `event_type`은 행마다 하나다. 재무 회신은 `scenario_id=BASE`면 `FINANCE_CONFIRMED`, 아니면 `AR_DATE_REVISED`.
- `REVIEW_OPENED.payload.rejudge=false`: 소유 문제가 트리거에 반응해 이미 다시 계산했다. 문제 4는 직전 버전을 `before`로 두고 바로 닫는다(사전 5.4).
- 하루 처리 순서: 지난 마감 점검(W1~W4·W6·W7, 보류 재개, 확정기한 경과) → 승인 회신 → 정시 수요 회신 → 순서표 행(seq 순) → 확정 입력(A5) → 상신 → 확정 가능 재계산 → 당일 최종 회신 경고(W5).
- 승인 회신 ID 접두어는 `ARP-`다(문제 3 상신 `APR-`와 구분).

### 9.6 (C) 조정자 확정 반영 (2026-11-15)

- 확정 가능(4.5 규칙 5 보강): 공급 `조건부`의 조건은 `condition_basis[].condition_type` ∈ {`inbound_unconfirmed`, `reorder_required`}다. 둘 다 승인 회신의 `공급조건부수용`(ref = 그 `supply_judgment_id`, 같은 버전)이 있어야 한다. `reorder_required`는 추가로 그 `po_draft_id`의 약정이 `승인`이어야 `확정 가능`이다. 아니면 `조건부 대기`.
- 승인 회신 모의 자료(S4-08 v2): `승인` 행은 회신 시점 공급 판정이 `조건부`면 그 조건을 명시해 받아들인다(`공급조건부수용` 추가). `거절`·`조건부` 행은 바꾸지 않는다 [가정].
- 재상신(4.4 commitment): 경로가 올라갈 때(순위 GRP_CEO > MS_CEO > MKT_TEAM·SCM)만 이전 상신이 있는 약정을 재상신으로 넘긴다. 내려가면 승인을 유지하고 재검토·재상신을 만들지 않는다. 마감은 다시 산출한다.
- 대체 확인: 모의 승인 회신은 `approval_request.superseded` 또는 `superseded_commitment_ids[]`에 든 약정에는 넣지 않는다(묶음의 다른 건은 유지).
- 사건 순서표의 상신(M04): 약정·회차별 행 `M04:<plan_id | PO:<po_draft_id>>:<회차>`(`event_type=APPROVAL_SUBMITTED`, `scenario_id`=마지막 경로 판정의 시나리오, 발주안이면 `target`=`발주안 <po_draft_id>`, `plan_id`=연결 기안). 문제 3 `deliverMock`이 이 행으로 상신하고, 같은 묶음으로 함께 나간 행은 `완료(같은 묶음 상신)`으로 기록한다.

### 9.7 (C) 통합 실행 뒤 수정 (2026-11-15)

- 4.5 규칙 2: 확정을 막는 열린 재검토는 `전제 변경`·`사람 판단`뿐이다. `기한 경과 후속`(회신 독촉, 예: 그룹 보고 미회신)은 막지 않는다.
- `reorder_required` 조건에 `po_draft_id`가 없으면 같은 기안·SKU의 최신 발주안(`p2.poDrafts({ plan_id })`)으로 찾는다. 없으면 `(발주안 미생성)`으로 대기.
- 종결된 기안(확정·철회·기한 경과 확정)에는 공급 판정 재검토를 열지 않고, 그 약정에 대한 모의 승인 회신도 넣지 않는다.

### 9.9 (D) 2차 수정 (2026-11-15)

- 재검토 전 확인: 공급 판정 재검토를 열기 전에 문제 2 `judgmentCheck({ plan_id, trigger_event_id })`를 본다. `checked=true, changed=false`면 재판정을 요청하지 않고, 사건 없이 재검토 표에 `종결`·`유지`(근거: judgmentCheck)로 기록한다. `changed=true`면 문제 2가 이미 새 버전을 냈으므로 직전 버전과 비교해 바로 닫는다(`rejudge=false`).
- 시연 기안의 기본 규칙: 그 기안의 지정 입력(사건 순서표 행)이 모두 지나면 9.8의 기본 규칙을 똑같이 적용한다. 판정불가(수요 미등록)는 규칙 대상이 아니므로 PLAN-005만 기한 경과 확정으로 끝난다.
- 결론 유지 사례: 재무 확인·회수일 변경 회신 뒤 현금 구간이 그대로면 `review`(`target_type=cash_window`)를 열고 바로 `유지`로 닫는다. `before`·`after`에 구간 전후 값을, `after.approvers[]`에 바뀌지 않은 승인권자를 남긴다. 회수일 지연 시나리오(07-10)는 같은 날 앞서 발주안 승인으로 구간이 이미 08-28이라 이 '유지' 사례가 된다. 화면: 모의 입력 화면의 '변경 입력 재검토(현금 구간)' 칸, 근거에 든 기안의 상세 화면.
- 구간 변경과 재대조 요약: 구간이 바뀐 `CASH_WINDOW_REVISED`에 `recheck_summary`가 있으면 `changed_commitments[]`만 경로 재검토를 열고(문제 3의 `ROUTE_JUDGED`로 닫힘), 결론이 같은 약정은 `cash_window` 재검토 하나를 열어 바로 `유지`로 닫는다(`after.kept_commitment_ids[]`). 결론 같은 약정에는 `ROUTE_JUDGED`가 오지 않아, 이전 방식으로 연 경로 재검토가 닫히지 않고 확정을 막았다.
- 발주안 상신 행: 순서표 M04 발주안 행의 `target`은 `po_draft_id`다(이전 '발주안 POD-…' 형식은 문제 3이 찾지 못해 발주안 상신이 모두 건너뛰어졌다).
- 이관된 요청: 재요청·정정 요청에 회신이 오면 그 요청으로 이관된 원 요청의 `기한 경과 후속` 재검토도 닫는다.

### 9.15 공급 확약·원료·생산 제약 반영 (사용자 요청 2026-11-15)

- 이름과 필드는 사전 v1.12(3.2 `inbound_schedule.supply_status`, `supply_commitment`, `baseline_replenishment`, 3.4 `plan_confirmability`, 10절). 새 사건 이름은 없다.
- 재검토 대응(4.4에 더함): `SUPPLIER_REPLIED`(공급 확약 회신·정정)와 `INBOUND_SCHEDULE_REVISED`(회신 반영·SCM 보충 계획) → 그 SKU와 `linked_plan_ids` 기안의 공급 판정 재검토. 문제 2가 회신 사건을 원인으로 다시 판정하면 직전 결론과 비교해 닫는다. 결론이 부족이면 대안 선택(직접 처리: 담당자, 자동: 9.8 기본 규칙)으로 잇는다. SCM 회신이 온 SKU의 `baseline_replenishment` 확인 요청을 닫고, 미회신 SKU는 열어 둔다(자동 해소 없음).
